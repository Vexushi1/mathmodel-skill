## 1. 要解决的问题与目标流程

用户要取消的是：在正常竞赛流程中，被要求另外安装校验环境、复制执行 Skill checker／同步／审计命令，再回传独立机器检查报告。这些操作不应成为用户在求解、绘图之外的必经环节。

当前并没有一个统一命名为“用户手动机器校验”的独立阶段可直接删除。实际问题分布在执行分工、流程图、交付命令的呈现，以及工具不足时的阻断和写入行为中。因此应原位整理现有契约与消费者，同时调整必要的执行逻辑。

数值阶段的目标流程是：

```text
模型已按原要求批准
→ 助手生成并检查代码，登记真实交付源码与输入身份
→ 用户按 full_fidelity 运行实际数值入口
→ 用户返回工作簿及必要的失败信息
→ 助手验收返回产物、更新项目事实并继续
```

| 阶段 | 用户的常规操作 | 助手的内部操作 |
|---|---|---|
| 模型与代码 | 明确必要条件，按原流程批准模型，运行实际预处理／主求解／required 深化入口 | 模型审查、静态工程检查、代码交付登记、返回工作簿验收 |
| 绘图 | 运行 MATLAB 绘图入口，查看图窗，调整并按需导出 | 字段／接口检查、来源与引用核对、项目同步和登记 |
| 论文 | 审阅内容与 PDF，反馈修改意见 | 模板检查、论文审计、正常编译和证明链生成 |
| 提交包 | 获取最终文件，按赛事渠道提交 | 按赛事范围打包、生成 manifest、完成包级验收 |

用户明确请求某项诊断或命令说明时可以提供；这不应反过来成为所有项目的默认操作清单。需要用户排除实际求解环境的错误时，应围绕真正的求解入口处理，不要求安装整套 Skill 校验环境。

## 3. 本次后续修订的范围

### 3.1 应完成的四项整理

1. **收拢执行分工。** 执行契约集中定义用户与助手职责；流程图和入口只保留动作主体或短引用。
2. **调整 MATLAB 原生分析的必要性。** 必需静态检查保留；助手环境可用时自动做原生分析，不可用时明确未覆盖项，正常项目交付不再要求用户代跑。
3. **保护资料不足时的项目事实。** 助手尚未取得材料或检查未完成时，不直接写结果失败；真实错误和已观察到的漂移仍按原规则处理。
4. **清理重复命令和检查清单。** 沿用现有验收、论文编译和打包入口，将内部操作移出用户流程，替换或删除被新分工取代的旧说明。

### 3.2 保持的边界

- 用户仍实际运行题目专属计算代码；助手不得导入或间接执行赛题入口，不降低数据、精度、时域、重复次数或容差。
- 数值入口内的质量检查、证据捕获和自动 RUN_RECEIPT 继续保留。残差、约束、收敛等要求不因取消额外 checker 操作而降低。
- 保留当前模型批准、源码与输入身份、accepted 工作簿和必要 03B 的含义；不把“用户说跑完了”改成 accepted。
- 保留 resolver 的原门禁清单和顺序，不新增统一 runner、用户校验包、项目表单、状态枚举或 gate。
- 不改变 A2／B2／C 显式协议的启用与消费条件，不以环境问题自动关闭 policy。
- 不重构草稿／终稿路由。当前“草稿论文”也触发 formal delivery 是已发现的独立问题，另立需求处理。
- 不承诺任意无 Python、无执行工具或无实际项目材料的会话都能完成正式验收；该能力缺口应如实保留，不能转交用户代跑，也不能伪造通过。

## 4. 具体修改方案

### 4.1 在原执行契约内定义一次分工

修改 `core/user_execution_contract.yaml` 的现有执行政策，明确 `execution_owner: user` 仅指真实数值运行。交付检查、返回产物验收、项目同步和内部审计由助手通过可用工具调用。

用户操作说明止于正常入口、实际产物和必要人工确认。检查器名称、命令参数、hash／状态写入等细节保留在助手工具接口和开发说明中。双 SKILL 入口如需说明，只作相同短引用，不复制整段政策。

代码模板把“助手交付检查 → 用户运行并返回工作簿 → 助手验收”写清楚。RUN_RECEIPT 明确是代码自动生成的记录，不要求用户另填。绘图仍保留用户打开图窗和人工确认，不把它误删成机器校验。

### 4.2 分离必需静态检查和可用时执行的原生分析

在 `core/code_quality_contract.yaml` 原位调整正式 MATLAB 交付准入：必需静态检查、当前配置、语义批准、源码闭包及真实输入身份必须满足；原生分析作为可用时自动执行的附加覆盖。该调整会降低无 MATLAB 环境下的交付前原生覆盖，必须明确披露。

| 正常项目交付情形 | 整体交付门 | 原生覆盖与处理 |
|---|---|---|
| 必需检查通过，原生分析完成且无真实错误 | `passed` | native 为 `passed`，保留诊断与摘要 |
| 必需检查通过，MATLAB 不可用或原生分析未完成 | `passed` | native 仍为 `unverified`，原因进入 warnings；只声称实际完成的检查 |
| 必需静态检查、配置、批准或来源检查失败 | `failed` | 继续阻断，不能被 native 的状态覆盖 |
| 原生分析发现真实错误、硬复杂度超限或源码不一致 | `failed` | 修复实际问题后再交付 |
| 显式要求原生证据的内部／维护调用 | 按该严格要求判定 | 保留现有 `require_native=True` 的强制语义，未核验不能通过 |

对 `scripts/validate_code_delivery.py` 的要求：

1. 解除 `--write/--strict` 与“必须安装 MATLAB”的隐式绑定；前者仍控制真实状态写入，后者仍对真实阻断问题返回失败。
2. 正常路径在工具可用时检查入口和全部声明的 `.m` helpers；两者采用相同分类，不能仅放宽入口。
3. 原生 adapter 返回的未完成诊断与真实失败分开消费；不把所有异常、文件错误或 `issues` 一概降为 warnings。
4. 必需检查成功后，按原事务登记实际交付源码与 bundle。整体 `passed` 只表示现行必需交付条件满足；既有 `native_analysis_status` 如实记录覆盖，不新建另一套状态。
5. 保留源码／输入在检查前后的重检、helper 闭包、诊断截断与脱敏。工具启动失败不能掩盖并行观察到的实际漂移。

`--matlab-command` 继续用于选择助手已有的原生工具，不作为用户额外操作要求。维护 CI 可以通过现有严格内部调用或对 native `passed` 的显式断言，继续要求真实原生证据；不得让 MATLAB job 因降为可选而出现“跳过但通过”。

不把 Code Analyzer 注入每个用户数值模板，不增加回执字段，也不把交付登记写成数值 accepted。底层 native adapter 原有 `unverified/failed` 区分应尽量保留。

### 4.3 在写入失败状态前识别上下文不足

先判断助手工作区是否具备本次检查所需的实际资料，再进入会写项目状态的验收路径。已有只读检查可先用于定位缺口；任何验收结论仍须绑定当前真实字节。

| 情况 | 拟处理方式 |
|---|---|
| 只返回了工作簿，所需源码／输入尚未传到助手工作区 | 记录具体缺失材料；不按“不存在于部分副本”判定用户实际运行错误，不提交 `rejected/failed` |
| Python／checker 无法启动，检查没有完成 | 报告未完成；保留项目事实，不把任务转交用户代跑，不授予新资格 |
| 已确认取得完整项目目录／材料清单，所声明输入实际缺失，或观察到来源冲突／质量证据失败 | 保留原阻断和负面结果处理，不能归为环境不足 |
| 已有 accepted 记录，但当前无法重新读取其完整来源 | 保留历史记录；本次不能凭旧记录或缓存恢复 `verified`，不能补写 validated 身份 |
| 上下文不完整，同时已观察到文件变更或真实身份冲突 | 继续记录／传播已知真实失效；上下文不足不是保留旧 current 资格的豁免 |

复用现有 `workbook_received/pending`、`execution_note`、框架“待办与缺口”等表达；只有实际收到并识别候选产物、且符合现有转换规则时才更新对应字段。不要为了表示“等待资料”覆盖历史批准、accepted 哈希或制造新的通过状态。

优先在原验收协调器中增加写入前的有界判断，必要时复用 `stage_inputs.py` 的观察事实；同时检查直接 CLI 调用，不能只靠自然语言提醒来保护写入。部分副本与真实文件丢失无法可靠区分时，保持未完成并请求必要原始产物，不做自动接受或自动拒绝。

不改变底层实际输入核验器对完整项目的严格规则，不扩大异常捕获，不让语法／Schema 错误、哈希冲突和数值矛盾被“资料不足”吞掉。已知真实变更仍走原 typed stale 和事务边界。

### 4.4 清理用户流程里的内部命令

- 03A／03B 直接改写流程图主语；项目级预处理同步核对。用户数值管线止于工作簿产出，返回后由助手验收。
- Python starter／pipeline README 去掉与 Authority 重复的用户操作清单，保留生成代码和 IO 所需的技术说明，不恢复已退休连跑 runner。
- 绘图 README 的独立 `sync_project.py` 命令移为助手接口说明或短引用，保留真实图像确认与按需导出。
- LaTeX 默认说明收拢到现有 `render_paper.py`；其内部已有正式 audit，重复的先行 audit 命令不再作为常规步骤。显式诊断入口仍可保留，独立模板 manifest 检查继续由助手完成。
- 提交 Pack 将打包与验收写成助手内部动作。packer 不自动完成包验证；原 `submission_package_validation` 仍须按 resolver 顺序执行。

正式 PDF 的审计／编译证明、包 manifest 等必要产物保留；“不让用户手动校验”不等于删除内部证明文件，或把 LaTeX 编译失败标成完成。

## 8. 成本、风险与回滚

预计为中等规模且边界明确的流程调整。主要成本是原生可用性与真实错误分类、资料不足时的安全写入，以及相关负例回归；用户流程文案应通过替换和删重收拢，不再叠加一层政策。文件数量可能包含多个消费者和版本载体，不能仅凭数量判断新增复杂度。

| 风险 | 控制方式 |
|---|---|
| 无 MATLAB 时交付前原生覆盖降低 | 如实报告 native 未验证；保留必需静态、来源、实际数值验收和可用时原生错误阻断 |
| 把所有原生异常或输入错误都降为 warning | 只处理已明确识别的未完成覆盖；真实错误、身份冲突和检查期间变化继续阻断 |
| 资料不足成为无条件接受或不失效的借口 | 不授予新 accepted／verified；已观察到真实漂移仍按原转换处理 |
| 检查整体 passed 被误读为全部原生验证完成 | 明确整体门的必需条件，保留 native 指标与简洁覆盖说明 |
| 去重时误删内部验收 | 复核 manifest 检查未包含在 render 内、packer 未自动验证等真实边界 |
| 减少用户操作却增加助手规则负担 | 单一权威、消费者短引用、复用原入口；不新增 Schema／runner／表单 |

业务回滚时恢复原工程契约和检查器判定，由 GitHub 重建元数据。放宽 native 必要性期间形成的实际数值与交付记录不能被伪写为“原生分析已完成”；回滚后触及的交付按当时现行规则复核，不批量覆盖历史 accepted、工作簿或模型批准。
