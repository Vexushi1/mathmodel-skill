从一个真实赛题看，先审题并标明各问之间需要什么数据或结果，再为当前问建立模型、完成挑战审查、取得用户批准。项目需要公共预处理时，先交付并验收公共工作簿，再交付该问的主求解代码。用户回传主结果后，按需要完成深化实验，随后恢复项目，推进下一道具备输入条件的小问。整题收尾单独核对所有必需小问。第 3 节修正这条路径上的推进条件，第 4 节修正据以认定数值结果有效的证据。

## 2. 实施顺序与拆分

| 顺序 | 独立主题 | 首次实施的判据 |
|---|---|---|
| 1 | 已验收的项目级预处理重复交付 | 先复现默认交付命令在下一阶段撤销有效验收；兼容原接口时按 patch 评估 |
| 2 | 当前问的批准、交付与回传范围；单问完成到全项目收尾的资格 | 两个方向都要有回归。可在同一主题中分提交；若另开两个 PR，后一个在前一个合并后的新 main 上验证 |
| 3 | 当前阶段缺少上游结果时的循环依赖诊断 | 先证明能区分真实互等与正常共享数据；只对明确可判定的依赖决策 |
| 4 | 主结果质量判据的冻结和返回核对 | 数值正确性优先项。先确定批准绑定、可机验字段、下游失效范围和新旧工具能力，再进入实现 |
| 5 | 正式运行规模的计划和实际证据 | 对现有回执版本作兼容设计，明确精确数量、最低数量、自适应停止的不同语义 |
| 6 | 普通深化实验逐项验收 | 可明确对应的必做方法先做表级覆盖；同一方法多实验、行级覆盖与负结果处理单列协议课题 |
| 后续独立小修 | 明确全流程请求的路由、达到限额后的检索报告 | 各自有成对正反例，可独立安排。整题工期估算先作为项目级使用建议，见第 6 节 |

首项修好后即可独立交付其价值。后续涉及同一权威文件的主题按顺序合并，并重审重叠差异。每个实施 PR 在最新基线上定目标版本：兼容修错按 patch 评估，向后兼容的字段、协议或能力按 minor 评估；若现有项目、CLI 或读取语义会被破坏，先按治理重新定级并提供迁移窗口。[变更等级与分支纪律](../SKILL_CHANGE_GOVERNANCE.md#L94-L171)

## 3. 第一批：恢复已经完成的工作，正确推进下一问

### 3.1 首个 PR 简报：项目级预处理重复交付

**触发场景。** `project_level` 项目已收到并验收预处理工作簿。随后交付 Q1 主求解代码，默认交付命令再次枚举项目内脚本。当前实现先将预处理状态写为等待运行、质量写为待定，再判断脚本哈希是否变化。主求解检查需要已通过的预处理，因此可能被刚刚写入的状态挡住。[默认命令](../core/module_manifest.yaml#L312-L316) · [状态更新](../scripts/validate_code_delivery.py#L676-L717) · [脚本发现](../scripts/validate_code_delivery.py#L916-L949)

**目标和操作。**

1. 通过正式 CLI 建立失败回归，记录交付前后的预处理状态、质量、工作簿身份、数据来源、当前阶段以及 Q1 能否继续。现有只验证指定脚本的测试可作为对照。
2. 在现有交付写入点区分首次交付、已验收且当前身份仍相符、已确认身份变化、证据暂不可用。优先复用现有输入观察与项目事务，核对实际源码、原始输入、已验收工作簿和原回执身份。预处理 1.0 涵盖单文件摘要和组合摘要两种历史约定。
3. 对复核一致的原验收保留有效资格，避免无意义的阶段倒退或仅为重查增加状态代次。发现实际变化走既有失效路径；读取失败或核查期间发生变化时报告本次无法确认，按事务规则结束或重试。交付器只能保留有证据的原资格。
4. 通过默认 CLI 再交付并重新恢复项目。检查主求解能够继续、旧资格没有被凭空授予、受影响范围正确，同一操作可安全重复。

**预计修改位置**为 `scripts/validate_code_delivery.py` 及现有预处理、事务回归。必查 `core/global_preprocessing_contract.yaml`、`core/user_execution_contract.yaml`、`scripts/validate_user_execution.py` 和项目同步路径；有需要时才改规则来源。此单以预处理 1.0 为界。深化脚本另有已验收源码整理、比较计划和证据绑定语义，其重交行为另案核对。[原始输入观察](../scripts/validate_user_execution.py#L672-L697) · [预处理测试](../tests/test_solver_backend_preprocessing.py) · [事务读集测试](../tests/test_project_transaction_read_set.py)

**验收与回滚。** 源码、输入、工作簿均相同时，连续交付两次后原验收仍有效；逐一改变任一项时，检查指出具体变化。再覆盖文件暂不可读、先前验收失败以及核查期间并发修改。候选定级为 patch，实施简报依当时版本填写目标号；保留既有 CLI 与工作簿格式。代码可单独 revert。已在项目中发生的真实数据变化按原始输入和原回执重新核实，仅凭回滚代码不能恢复项目资格。

### 3.2 第二个主题：单问可以开始，全题何时可以收尾

**两个方向一起定义。** Q1 已批准、Q2 等待 Q1 的结果时，只针对 Q1 的主求解应能开始。Q1 已有有效结果而 Q2 仍待处理时，可确认 Q1 完成，但切换全题收尾必须核对所有必需小问。当前 `--question` 的证据按单问恢复，而全流程恢复分支会据传入的结果集合选择收尾；这里需要区分两个资格范围。[证据适用范围](../core/runtime_assurance_contract.yaml#L170-L180) · [阶段选择](../scripts/resolve_workflow.py#L487-L519)

1. 从 `resolve_runtime.py` 跟踪当前问、阶段、项目与当前状态快照，直至返回的检查命令和 `reading_plan.tool_interfaces`。以既有 resolver 返回的有序门为执行清单。为每个门决定适用范围：模型批准支持既有 `--question`，代码交付定位本阶段具体脚本，结果验收定位本次工作簿。首次未登记源码走显式指定入口，单凭标准文件名不能取得交付资格。
2. 拟从单问切换到全项目时，使用同一份当前状态重新核对全项目所需各问的主结果、适用的深化结果或有理由的免做决定。尚有待完成问时，报告该问及所缺证据；已有结果的当前问保留单问资格。
3. 全项目数值后端、共享输入、整份语义记录完整性和跨问失效传播维持项目范围。受损状态或真实的全局不一致依既有保护处理。兼容入口没有项目证据时，维持其已有的无状态行为。
4. 驱动正式 resolver → 实际门命令 → 下一次恢复，双向断言。检查有效计划、读取计划、等待点和实际命令一致。附加对照包含独立问、真实缺上游、首个未登记脚本、一问已完成和全部必需问已完成。

查阅 [批准检查](../scripts/validate_model_approval.py#L175-L209)、[项目语义事务](../scripts/validate_semantic_governance.py#L205-L242)、[工具接口投影](../scripts/reading_plan.py#L886-L895)、[首次交付测试](../tests/test_v10_project_delivery_receipt.py#L81-L85)。如改动触及计划结构或 CLI，在实施前给出旧消费者的兼容示例与回滚方式。

### 3.3 第三个主题：未解的必要上游循环

审题将依赖分为 data、parameter、model、result。状态转换引擎能报告环并有限终止；一个环形路径不足以说明两个小问都在等待对方最终数值。设计改动应落在**当前问、当前阶段的执行准入**：追踪必需的输入对象和是否已有当前有效来源，只有未满足的必要依赖形成无起点闭环时，指出涉及哪两问、各缺什么，退回审题或模型设计。保留历史未分类依赖的诊断；真正的耦合问题在模型方案里写明联合求解，或明确迭代初值、更新与停止条件。验收涵盖顺向依赖、确有起点的计算、相互等待以及环外独立问；若目前的数据不足以区分上述情况，先提供诊断，延期自动阻断。[审题合同](../modules/01_problem_audit.md#L57-L73) · [类型与环策略](../core/state_transition_contract.yaml#L285-L319) · [已有循环回归](../tests/test_v900_state_transitions.py#L215-L231)

## 4. 第二批：按事先作出的承诺验收结果

### 4.1 主结果质量规范（PQS）：先绑定，再比较

**基线与风险。** 模型设计要求预先确定判据，但框架的 03A 检验栏目前是自由文本。模型批准绑定语义版本和结构化模型身份（SIB），现有数值检查器按回传工作簿中的判定关系与阈值复算。若批准误差上限为 5%，工作簿误填为 10%，实测为 7%，只复算表内关系会得到错误的达标判断。[框架现有槽位](../templates/model/model_paper_framework.md#L393-L416) · [模型批准与身份](../core/model_approval_contract.yaml#L150-L199) · [数值规则](../core/numerical_verification_contract.yaml#L57-L111)

**协议决策和实施次序。**

1. 在现有框架的逐问验证方案中，为可机器核对的 PQS 定义一种确定的表示，给出规范化、唯一 ID、指标、必要单位、方向、阈值、来源、证据表和适用范围。先复用已支持的五种关系：小于等于、大于等于、绝对值小于等于、等于、布尔真。领域指标只能核对汇总时，报告相应证据范围。
2. 在同一次人工批准中绑定当时展示的判据版本，框架保存原始条目，状态与交付只引用可校验的身份。改动数学误差要求、只整理文字、表名变化三者须分别定义失效范围。若采用 SIB 扩展，先核对多模型比较会保留扩展字段的现有投影；比较结果或纯措辞变化会误触发模型变化时，另选能绑定同次批准的表示。compact 生成、full 展开与跨聊天恢复都必须保留批准依据。
3. 贯通模型批准 → 代码交付 → 结果回传 → 下一次项目恢复。按 ID 比对原定要求与回传条目，再检查实际结果及底层证据。把批准来源纳入事务读集，防止验收过程中文件变化。协议需明确非阻断条目如何表达；旧严格协议中失败行仍按原规则处理。
4. 用“批准 5% / 回传 10% / 实际 7%”、漏掉必做项、重复 ID、方向或单位错误、布尔项、单纯重排、措辞编辑和并发变更作回归。旧项目缺少冻结记录时，保留原验收的历史含义；重新交付按新协议时从可核实的设计与明确批准建立绑定。禁止从历史结果反推当初的批准值。

**影响面。** 数值规范、模型批准、框架实例化、工作簿规范、交付与验收、恢复和同步，以及 Python/MATLAB 两端。协议选型在本主题的简报中落实。若缺少能分辨新旧资格的可靠方式，先停在设计阶段。[框架实例化](../scripts/instantiate_model_paper_framework.py) · [数值回归](../tests/test_v714_numerical_verification.py) · [验收回归](../tests/test_v714_receipt_fail_closed.py) · [模型身份回归](../tests/test_v900_semantic_identity_binding.py)

### 4.2 正式执行规模：计划、实际与停止证据

在对应阶段交付前冻结规模语义，复用 `RUN_CONFIG` 和 `RUN_RECEIPT` 的角色。当前协议核对求解器、种子、容差及迭代或时间上限，重复次数、场景与网格或时域主要作为实际运行事实。先为确有需要的维度定义“精确数量 / 最低数量 / 已批准的自适应停止条件”，并区分数量和集合身份。迭代上限只规定可用上限。[当前计划与实绩字段](../core/user_execution_contract.yaml#L417-L463)

- **正反例。** 要求 100 次、返回 80 次应能定位；要求至少 100 次、实际 120 次可通过该项；批准误差界触发停止、第 80 次满足条件且证据可追溯，应通过该项。场景数相同但漏了必测场景，仍需指出场景差异。
- **证据深度。** 对需要证明的维度读取已有场景标识、运行记录、网格/时域边界或停止证据。仅有计划和回执两个相同数字时，明确本次能验证的是声明一致性。区分性能估算和正式数学承诺，保留已有全量精度、输入身份、上游工作簿、实际停止原因和源码绑定。
- **兼容。** 分别列预处理 1.0、普通数值阶段 1.1、带辅助输入的 1.2，以及拟议新协议的读写能力。覆盖新工具读旧产物、旧工具读新产物、版本漏标、未知版本、可选协议组合和新产物重试。使用固定基线工具验证其实际行为；若旧工具无法拒绝新语义，须由版本协商及最低 reader 限制新资格，不能把旧工具成功记作新协议通过。先确定可运作的版本边界，再发布新 writer。[执行协议实现](../scripts/execution_protocol.py) · [回执回归](../tests/test_p5b_run_receipt.py)

### 4.3 普通深化实验：先补已知漏项，再扩展协议

主结果 accepted 后先判定是否需要深化。若有充分理由免做，正常推进。若必做，在交付深化代码前冻结相应实验与判据。现有普通 `analysis_methods` 为字符串列表，两类比较实验已有专用冻结计划和比较值校验。[深化状态字段](../core/project_state.schema.yaml#L1903-L1921) · [冻结和比较范围](../core/user_execution_contract.yaml#L308-L353)

**先实施可精确定义的覆盖检查。** 对已登记、能与标准表无歧义对应的普通方法，按必做清单检查每一张对应底层表有实质数据。例如，参数敏感性和场景压力测试都必做，只返回前者，应报告缺少压力测试。保留自定义历史方法的原义。普通压力表使用场景、条件、结果等字段；直接并入现行比较表映射会额外触发基准值、对照值、差异核对，必须分别投影两类表的专属要求。[工作簿定义](../core/workbook_schema.yaml#L206-L248) · [现行校验分支](../templates/code/hsk_pipeline/workbook_validation.py#L234-L256)

**再评估版本化覆盖。** 同一方法对应多项场景或实验时，表存在只能证明表级覆盖。需要逐项完成证明时，设计必做实验标识、场景范围、底层定位和处置；技术完成、负面科学结果、缺失证据分别记录。普通旧路线把“是否保持”为非真的行判为返工，混合比较也有现行回归。新策略应显式区分附加主张需收窄、主答案需重算、模型本身需重新设计。对只更改深化计划的情形，保留仍然有效的主结果。验收包含普通、两类比较、混合工作簿、自定义旧名称、同表缺场景以及真实负面结果。[普通回执判定](../scripts/validate_user_execution.py#L404-L430) · [混合实验回归](../tests/test_analysis_comparison_integration.py#L446-L519)

## 5. 两组贯穿验收与记录方法

| 项目夹具 | 操作步骤 | 下一次恢复必须看到什么 |
|---|---|---|
| 三问、无统一预处理 | 在 `not_needed` 项目中设置 Q2 依赖 Q1 最终结果、Q3 独立。从 pending 起步，经实际 resolver 等待点和作用域明确的测试批准，交付 Q1、验收回传、恢复；再推进 Q2 与 Q3 | Q2 待批准不挡 Q1；未产生必需上游结果时 Q2 等待；Q1 完成只授予单问资格；Q3 能独立开始；全部必需问满足证据条件后才进入全项目收尾 |
| 有统一预处理 | 在 `project_level` 项目中运行并验收公共工作簿，交付主求解、重复交付、重新恢复。另一次只改变一份共享输入 | 输入相同时保留有效资格。真实共享输入变动时，按实际输入依赖复核，即使 Q3 不依赖 Q1 的输出，也可能受同一工作簿影响 |
| 两组的单因素对照 | 轮流替换已冻结阈值、删掉运行场景、漏做实验、改动正在验收的文件。另保留无需深化、旧档只读和局部说明文字修改的对照 | 错误定位到具体小问、阶段、承诺和证据；回滚或重试能从一致状态恢复。旧产物不自动获得新资格 |

每项同时核对有效计划、实际命令、状态与工作簿、下一次恢复。哈希夹具适合检查选了什么阶段；已有 Python/MATLAB 合成烟测适合验证真实运行、XLSX 与回执交接。凡预置了部分状态的测试，记录跳过了哪些环节。测试中的批准与数值证据限于维护夹具；真实赛题仍由用户按原合同运行。[恢复夹具](../tests/test_solver_backend_runtime_resume.py) · [双后端烟测](../tests/solver_backend_mixed_smoke.py) · [项目证据范围](../core/runtime_assurance_contract.yaml#L170-L180)

## 6. 次要修改与项目级排期

- **自然语言路由。** 仅对明确表达完整流程的情况修复错误筛选。正例“请按全流程，先审题，最后终审”应在既有批准点暂停；对照“请审阅这个全流程，只给意见”应只读。保留否定句、显式意图、现有两个有界动作组合及正式/兼容入口的既有差异。未明确要求完整交付时，不能仅凭“最后终审”推断全流程。按原动作基线和新正反例验证。历史维护已拒绝通用混合计划组合。[路由判断](../scripts/resolve_workflow.py#L72-L91) · [已有路由裁决](../docs/v10_27_runtime_nonregression_closeout.md#L25-L53)
- **文献检索覆盖。** 沿用现有配额、状态枚举和 E0 证据等级。达到总配额时，在已有停止原因与未解决问题中列出未执行的查询；尝试清单只记录真正的请求。离线模拟“前三词各命中十条、第四词未查”和“最后一个词恰好达到上限”。本项按独立报告修错评估。[检索实现](../scripts/literature_search.py#L279-L323) · [现有离线测试](../tests/test_literature_search.py)
- **整题工期与算力。** 先在昂贵且阻塞后问的具体项目中，利用框架的“全项目数值实现”和现有批准摘要记录单次代价、调用次数、可并行部分、依赖问与重跑余量。简单项目按现有最小流程。估算用于排期；调整数学精度、样本量或已批准停止条件时，回到相应设计/执行规则。如果多个项目仍有可复核的同类缺口，再按治理第 14 节评估是否提升为公共能力。[现有框架](../templates/model/model_paper_framework.md#L16-L23) · [求解器适配与成本](../modules/02_model_design.md#L459-L476) · [治理准入](../SKILL_CHANGE_GOVERNANCE.md#L334-L345)

## 7. 每个主题的仓库操作、交付与回滚

1. **取基线、查重叠。** 从届时 main 读取 bootstrap、治理和对应权威文件，记录版本、SHA、默认分支、开放 PR 和相关未合并分支。与其他工作碰到同一权威文件时，先串行处理，再基于新 main 重审。
2. **写实施简报。** 写明当前与目标版本、等级、直接目标、范围外和禁止触碰文件、预计改动位置、必查关联、正反例、迁移与回滚。首次实施从第 3.1 节开始。按治理第 6 节，一次维护聊天只负责一个明确分支，一个实施 PR 只承担一个主题。计划分支用于审阅这份文档；后续实施另起维护聊天，从届时的最新基线开分支。
3. **验证基线行为，完成最小修改。** 先用正常入口和现有夹具证明差异，再修改承担规则的源头和必要消费者。涉及工作簿时核对 Python 写入、验收及 MATLAB 交接；涉及状态时核对 Schema、同步、读集和失效传播。逐项说明看过哪些相邻文件以及为何无需修改。保持历史期望可追溯，不靠削弱断言取得通过。
4. **兼容与回滚先于发布。** 每项 PR 说明旧 CLI/工作簿/字段的读取窗口、何种操作会切到新语义、最低 reader、兼容层退出条件、如何停用新 writer。代码回滚采用单主题 revert；已经写入新协议的项目保留原始证据，使用相应 reader 核实。回退涉及项目数据时依照现有事务和真实来源处理，不能倒填用户批准或把历史结果自动记成新版本验收通过。
5. **远端生成和验证。** 提交源文件，由 GitHub `refresh-generated` 维护索引和 MANIFEST，记录源提交、生成后的最终 head 及实际 checkout。开发和 draft 阶段核对专项是否真的被运行；固定 targeted 清单外的用例须在对应远端运行中取得结果。进入正式验收时按仓库治理核对 Windows Python 3.10/3.14 各四分片及汇总、静态与生成检查、Windows MATLAB 原生数值链、LaTeX 基线与适用的 Optimization baseline。无须为此计划重写 CI。
6. **冻结、合并和交接。** 最终 head 发生变化需要重新验收。核对审阅和正式检查后再合并，随后核查合并后 main 的 run。主题完成报告记录 PR、最终 head、合并 SHA、远端运行、兼容性和未核验范围。计划文档的合并仅代表维护路线可供引用，各实现主题分别取得证据。

治理与远端入口见 [修改简报与影响面](../SKILL_CHANGE_GOVERNANCE.md#L47-L90)、[生成与正式验收](../SKILL_CHANGE_GOVERNANCE.md#L196-L259)、[兼容与完成报告](../SKILL_CHANGE_GOVERNANCE.md#L263-L330)、[PR 模板](../.github/pull_request_template.md) 和 [实际专项清单](../.github/workflows/ci.yml#L72-L96)。
