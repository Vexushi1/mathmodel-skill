# 数学建模 Skill 全文启动与阅读架构重构计划

> 审阅草案，2026-11-20（北京时间）。以 [main v10.35.3](https://github.com/Vexushi1/mathmodel-skill/tree/4f765d3e1326d3ca7555933059e9313f99b86347) 为比较基线。目标是一次替换默认的阅读架构。本文件记录拟实施的结构、边界、切换和验收，当前业务规则以所链接的原始 Authority 为准。

## 1. 要解决的大问题

用户实际使用中，强制模型完整读完 Skill 再开始建模时效果可接受，改为按需加载后，出现规则少读、审题粗略、代码规范没有落实等体感退化。这个反馈确定了本次重构的默认体验。**正式数学建模先取得整套现行规则全文，核对覆盖后开工。**

目前默认逻辑是先根据请求选择路线，再决定读哪部分。即使某次选对了路线，正文读取器仍逐次返回一个来源的一块，后续取读取决于调用方。修复终审或某条绘图路由只能改相应场景。结构改造要把**正式任务开工前的全文读取**变成独立步骤，把任务路由交还给业务运行时。

现有多个入口的约定必须一起迁移。Bootstrap 和插件默认提示明确要求最小加载；运行时是在完成业务路由后才生成读集；写作合同还规定到下一写作阶段才取该阶段资料。切换时统一修改这些约定，允许开场预读全部规则，同时保留逐章取用当前规则和写作前置条件。 [Bootstrap](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/core/bootstrap.yaml#L35-L55) · [插件默认提示](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/agents/openai.yaml#L4) · [运行时组装](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/resolve_runtime.py#L727-L742) · [写作合同](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/core/writing_runtime_contract.yaml#L234-L253)

## 2. 重构后的默认链路

**固定 Skill 版本 → 取齐全文并核对 → 进入当前项目并读题面、附件 → 运行原有业务路由 → 逐阶段校验实际成果。**

完整比赛、新建模项目和范围未限定的正式建模请求，统一采用全文启动。用户明确只查一个字段、解释一条规则、或只做已经定型的局部调整时，才选局部读法。任务后来扩成正式建模时，在推进前先完成全文启动。工具缺文件、上下文容量不足和超时都进入缺口处理；读取策略的改变由显式请求决定。

开场预读覆盖审题、建模、预处理、求解、深化、图表、写作和终审规则，以及各阶段的条件分支。读到后续规则只表示助手已取得正文。Model Challenge、人工批准、用户本地全精度数值运行、已验收工作簿和各正式检查仍由其业务 Authority 触发，原顺序仍由解析器决定。 [当前运行阶段及暂停点](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/core/workflow_router.yaml#L52-L135)

## 4. 全文到底包含什么

全文范围是**当前发行版所有承担正式运行规范的正文**。第一步逐件审定角色，因此文件只要实际定义正式任务的行为，就会进入全文范围，即使其分支此时尚未激活。按项目发生的实际数据与批准事实，在相应步骤读取。

| 分类 | 纳入或使用方式 |
|---|---|
| 启动和基础合同 | 启动入口、跨阶段政策、业务路由和阶段、题型、状态与产物职责，以及实际定义运行行为的合同原文 |
| 全部业务模块及生效分支 | 审题、建模与批准、03A／03B、预处理、图表、各载体写作、初审和终审，包含模块间引用的规则正文 |
| 现行专业包和规范模板 | 已登记题型、竞赛与载体包，Python／MATLAB 的规范说明，工作簿、图表和论文模板中具有规范作用的 manifest、字段定义和说明。某项规则若只有模板或程序里有定义，先纳入该原始来源，再决定正式重构时归属 |
| 机器执行、样例和开发材料 | 代码工具本体、合成数据、测试、历史维护记录、生成导航、示例作品和二进制资源逐件说明用途。机器执行和确有参考需求时使用；同时承担规则职责的文件按上项纳入 |

每项至少登记相对路径、角色、是否纳入与原因、依赖或规则出处。构建时生成稳定的排序和每份原文的长度与内容身份，新出现且未分类的潜在规则来源应在仓库检查中暴露。做一次独立的规则对照，避免把当前解析器已经遗漏的文件从全文范围里也一并漏掉。同一原文存在经过校验的物理别名时可减少重复投递，报告中仍保留其角色和来源路径。

基线 Git 树中，单算 `core/`、`modules/`、`packs/` 已有 69 个文件、1,063,522 字节，含生成导航，且尚未计入规范模板。这个数字只说明规模，最终范围和宿主可承载的实测容量需单独确认。文件索引负责导航，`MANIFEST.sha256` 负责包完整性，均须由独立规则角色来界定全文。 [当前基线目录](https://github.com/Vexushi1/mathmodel-skill/tree/4f765d3e1326d3ca7555933059e9313f99b86347) · [清单哈希的现有语义](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/generate_indexes.py#L195-L223)

**减重作为架构整理来做。** 先把重复规则收归一个权威，分开规则正文、工具投递、例题和开发记录。能证明语义相同的重复说明才合并；唯一规则、单位、阈值、例外和前置条件要逐条映射到新位置。保留当前发行版全文作为效果对照。若旧全文无法在目标宿主稳定送到，先整理有效正文再重新验收；由完成范围的真实覆盖决定能否宣称全读。

## 5. 怎么验证真的取齐，谁负责

1. **固定版本。** 使用已选完整提交，绑定受管理清单及各个来源身份。清单生成避免把自身或不断改变的分支 HEAD 嵌入校验，发布时以实际固定提交确定其身份。机器实现分别核对 Git 原始内容和现有分发哈希语义。
2. **逐件取回。** 每一份规则全文按首行到末行取回。读取器与宿主核对实际正文、文件路径、版本和分块顺序，发生缺段时主动补取，分块同时考虑响应字节上限及超长单行。去重只用于同一版本、内容一致且可验证的来源。返回正文和分块校验分别使用已有机制。
3. **记录完成状态。** 区分来源已列出、原文范围已取齐、宿主已送达本次模型输入、成果应用复核。缺尾段、整个文件缺失、不同提交、正文截断和缓存身份过期均应报告。展示给用户的是完成比例或具体缺口，工具负责取读。报告范围绑定本次会话，已有授权和项目状态分别沿用原合同。
4. **进入任务和恢复。** 输出开场是否满足全文覆盖，满足后按当前请求进正式动作。长对话换阶段、换问或换章时重新取得当前所需原文和证据；跨会话恢复或 Skill 版本变化重新建立全文启动的覆盖，现有项目事实根据当前 State、框架和工作簿恢复。读取状态放在宿主或诊断记录，业务 State 保留批准与项目事实。

**两类环境的能力不同。** 可控宿主可以检查实际输入和容量，在覆盖后才启动正式动作。仅有 ChatGPT＋GitHub 连接器时，助手在首个动作中按同一份清单取得原文并补齐缺段；对模型内部保留了多少正文、平台是否裁剪或压缩，按可观测证据分别记录。若正式宿主要求首个模型请求同时包含所有规则，核对有效上下文容量并为题面、项目资料和回答预留空间。无法证实满足这项要求时，记录其未验证状态；取得正文受限时报告实际缺口。读取传输可验证，数学理解、执行和产物质量要通过单独的成果检验。 [既有固定身份与分块读取](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/read_stage.py#L252-L328) · [既有覆盖校验](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/reading_plan.py#L48-L176)

## 6. 实施、切换与回滚

| 工作包 | 主要改动 | 进入下一步的条件 |
|---|---|---|
| A. 盘点与实验基线 | 固定当前发行版，审定现行规则清单，标出重复、实际依赖和现有按需入口。用项目合成夹具与当前 Skill 做一轮按需／全文对照 | 预期清单可独立复查；至少找到一组真实工具轨迹，以及其匹配的实际输出 |
| B. 整理规则和统一入口 | 明确原始规则职责，合并可证重复并迁移旧默认；生成全文目录。把多个入口和写作读取时点收归同一合同 | 对照表覆盖原始依据、阈值、例外、条件和阶段暂停；文档与机器检查一致 |
| C. 接通实际取读与启动 | 复用现有读取器，接入独立于任务意图的全文取读入口，累计完整块并接入宿主。加一组固定版本、缺源、错版本和失效的反例 | 正式启动实测覆盖全部审定正文，遗漏和截断会留缺口，局部用户请求走明确入口，读完只有启动意义 |
| D. 整体验收后切换 | 用同一批题完成实测，比较当前按需、当前规则全文预读和重构后全文预读三组，确认规则保全和成果质量后一次切换正式默认。清理被替换的默认指引，保留明确的兼容入口 | 目标宿主能交代取读和容量，正式启动及业务验收通过。容量和成果仍无证据时保持候选，先复核规则整理或宿主支持 |

这是一次完整的架构迁移。A–C 可以分阶段评审并保留可回退的源提交，生产默认在 D 一次切换。历史固定版本继续从其原入口读取，新旧协议通过显式入口区分。旧工具和项目兼容测试保持，预先整理接口、暂停行为和切换说明；未来版本等级按实际默认行为、CLI 与旧项目兼容影响决定。可单独退回上一条稳定启动链，原批准、证据和已有计算资料按各自身份重新核验。此时草案版本仍从当前主干比较。

## 7. 验收方法

使用同一批可控题目和附件作为对照，由实施者建立并跑样本。正式任务测试建议包括：

- **全读取证。** 规定范围内每份规则从首行到末行都有可核对正文在正式动作之前返回。针对整份规则漏掉、尾段缺失、同长度却变了内容、错提交、同名不同来源、容器或连接器只看见摘要、范围在会话中扩大的反例都要有断言。
- **原业务约束。** 对照同一项目下的题意冻结、模型挑战与用户批准、执行回执、数值证据、图表和写作检查。特别核对读过有关求解和终审的规则之后，仍按项目的当前等待点推进。
- **真实成果对照。** 用一题末页有限定词、附件表注有单位、跨问存在依赖的合成题。独立复核逐问需求地图与建模约束。用相同批准模型核对 Python／MATLAB 源码是否实现目标方向、单位、约束和实际入口，并记录静态检查的告警、阻断、原生覆盖和回传证据。用户只需审阅试验结果。
- **真实分发与边界。** 分别在实际使用的 ChatGPT＋GitHub 和有正式执行能力的环境做可重复对照。控制模型、设定、提示、附件及停止点，保存真实工具响应与成果。登记实际返回量、等待和未观测能力；内部 Token、上下文保留与压缩等依据实际环境可见证据报告。仓库自动化、用户端操作和成果判断分别留证。

成功的判据是新默认能复现原来全文模式的审题和代码质量，并使开始前的全文范围及缺口可查；若实测无法获得有效全文投递，先解决宿主容量或权威正文整理。前序批量读取试验只验证过有限样本，小批读源的性能数据可复用，但实际宿主完整投递仍是本次独立准入。 [前序批量读取与宿主缺口](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/docs/v10_27_runtime_nonregression_closeout.md#L25-L53) · [既有连接器受控试用](https://github.com/Vexushi1/mathmodel-skill/pull/275)
