# 数学建模 Skill 正文读取、审题与代码交付可靠性计划

> 审阅草案，2026-11-20（北京时间）。以 [main v10.35.3](https://github.com/Vexushi1/mathmodel-skill/tree/4f765d3e1326d3ca7555933059e9313f99b86347) 为比较基线。本文供实施评审；现行业务规则以各自的 Authority 为准。后续每个实施主题从届时的 main 重新核对、单独验收。
>
> 本计划接续 [分阶段读取重构与受控试用](stage_reading_execution_refactor_plan.md#12-风险推进看板与下一次接手方式)。[#326 工作流作用范围与数值验收计划](https://github.com/Vexushi1/mathmodel-skill/pull/326) 记录的是逐问推进、状态恢复和数值验收等前序工作。这里关注模型能否取得当前动作的原始材料，并按照已有标准完成审题、建模、代码和后续成果。

## 1. 目标与优先级

用户体验中有三种需要分别查证的现象：模型只翻一部分规则，审题漏掉题面细节，生成代码偏离工程或求解规范。优先追踪以下四个事实。

| 要核对的事实 | 依据 | 失败时先查 |
|---|---|---|
| 应读的来源是否选全 | 当前动作、路由、模块及业务 Authority 的独立预期清单 | 路由选错、当前小问或阶段判断错误、项目材料或条件分支漏选 |
| 适用正文和原始输入是否取齐 | 实际工具返回的正文、页码或行范围、项目材料身份及返回时序 | 首块即停、截断、附件无法访问、旧摘要替代当前材料、条件尚未裁决 |
| 既有校验是否在正确范围执行 | 实际命令或工具结果、当前小问和阶段、源码或项目快照身份、告警和阻断项 | 只看计划没执行，检查了别问、旧源码或其他后端，环境只能提供部分分析 |
| 规则与项目事实是否落实进成果 | 逐问需求地图、当前 Problem Contract、批准模型、源码、工作簿、图文或审查成果的独立对照 | 漏了限定词、公式或数值语义，现有检查覆盖不到，或模型未应用已经取得的正文 |

当前最高优先级是把**选源、取读、检查和成果证据**连在一起。缺哪一层就修哪一层。仓库静态审阅可以确认若干缺口；用户某次实际会话的根因，仍需看到当次请求、实际取读和产物后判定。

## 3. 已确认的缺口与待验证的原因

### 3.1 来源选取和实际取读

- **终审规则与清单有落差。** 现行项目记忆合同要求全文写作、跨问综合、跨会话恢复和终审读当前完整框架。普通终审的 `read_now` 主要列 Skill 规则，现有项目正文行只在特定配置分支生成。写作阶段入口还会独立取源。仅消费某个计划字段可能错过当前框架全文。 [项目记忆合同](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/core/workflow_router.yaml#L24-L40) · [项目行与读集生成](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/reading_plan.py#L780-L851)
- **混合绘图可能少选业务资料。** 通用绘图计划检测到“机理图”后可提前进入机理图配置，遗漏结果图合同、实表读取和 QA。带有 draw.io 等长关键词时还要从自然语言入口验证，判断是否在上游意图评分就丢掉结果图。直接切到通用全量路径也需要核对两类图的现有模板是否都入集。 [选读顺序](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/reading_plan.py#L631-L670) · [两类图规则](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/core/workflow_router.yaml#L535-L553)
- **单次成功取块无法覆盖阶段。** `read_stage.py` 默认只返回一个文件的一个块，120 行；`remaining_ranges` 表示该次返回范围的缺口。现有测试能主动取全块并重组。真实会话是否继续请求后续块，以及能否在换小问或长对话后取齐，需要通过工具返回和成果检验。 [读取器](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/read_stage.py#L295-L344) · [既有宿主试用](https://github.com/Vexushi1/mathmodel-skill/pull/275)

### 3.2 为什么审题可能不仔细

Module 01 已要求逐句拆题、逐问记录原始对象、给定量、约束依据、附件字段角色和前问依赖。改变答案的关键歧义应保持 `pending`。但题面和附件是外部输入，阶段读取器对未映射的 `original_problem_text` 或 `current_problem_contract` 可只返回待解析项目输入。后续语义治理检查的是当前 State 和框架记录，检查通过本身无法解释原 PDF 末页、脚注或附表单位是否被正确理解。**规则读齐、原题读齐、审题答对需要分别验收。** [审题 Module 01](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/modules/01_problem_audit.md#L7-L47) · [外部输入及待解析项](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/read_stage.py#L178-L189) · [语义治理的输入](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/scripts/validate_semantic_governance.py#L156-L219)

实际个案重点检查：题面或附件当时是否可访问、是否取到末页和表注、每问必须交付什么、范围与单位有没有被默认值改写，以及“来自前问的数据”和“依赖前问结果”是否混淆。论文问题重述是新动作，应再次对照原题和已冻结的 Problem Contract。 [论文重述和问题分析](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/core/writing_runtime_contract.yaml#L370-L386)

### 3.3 为什么代码可能偏离规范

主求解阶段要求恢复当前批准模型和合法数据入口，从项目选择的后端加载对应模板，再按代码质量合同生成、静态检查与交付。主求解、深化、统一预处理和绘图的职责各有边界。一个用户反馈可以具体归为四类：

1. **规范未取齐。** 当前阶段的业务模块、后端模板或工程合同漏选、被截断，或模板来自另一阶段／后端。
2. **检查未实际执行或检查对象不对。** 仅列出命令，或实际运行用了旧文件、其他小问、另一份源码 bundle。需核对实际项目根、阶段、后端及源码身份。诊断调用若未采用正式严格参数，还需读取报告内容和退出语义，不能仅凭退出值 0 判断通过。
3. **机器判定为告警。** 行数、函数长度、参数数等含推荐值、告警与阻断阈值。MATLAB 原生分析不可用时，现行合同允许满足必需静态条件的代码交付，并要求如实记录原生覆盖。产物仍可读性差，应逐项看报告再决定是否修订治理阈值。
4. **现有检查未覆盖该语义。** 静态检查和受限的模型—代码一致性核验能发现具体类别的问题。题目目标符号、单位换算、时序、约束与模型是否等价还需对照当前批准模型。真实执行和回执分别回答运行与结果证据问题。

## 4. 实施工作包与依赖

### 0. 冻结验收基线，先复现

当当前项目仍在等待明确批准或用户回传时，停在该处属于基线的正确结果。比较代码质量应为两个候选提供同一份当前批准模型及对应后端。

- 从届时主干、业务规则和案例事实独立推导预期读集、当前动作和应有成果，再跑现行解析和读取。每例记录来源版本、阶段／小问、必读原文和条件、正文是否在动作前到达、现有检查及产物结论。
- 代表场景包括新题审题、跨问恢复、混合图、纯配色、逐问写作中的证明与算法、终审，以及 Python／MATLAB 代码交付。
- 优先各留一个运行失败前后的可复查样本。用户真实运行日志缺省时用合成夹具复现仓库机制，现场根因仍列待验证。

### 1. 当前项目正文读取，先修终审

在明确的终审场景，让计划和正文工具消费当前项目的完整框架，覆盖普通审查路径中已确定的正式终审与 `writing_stage=final_review_and_delivery`。复用项目快照、来源哈希与 `origin=project`。已确定需要项目证据、但框架缺失或过期时，在读取诊断中列出缺口。无项目的新题正常审题；普通单问按适用的小问、依赖及相关共享栏目取读。整篇写作、跨问综合和明确恢复逐个核对后纳入。

实施定位 `core/workflow_router.yaml#project_memory_contract`、`scripts/reading_plan.py`、`scripts/read_stage.py` 及现有测试。验收用两问项目验证取到 Q1、Q2 和独立共享尾节；用无依赖单问、旧摘要、计划后框架变更及状态代际变更做对照。具体数值继续回到已验收工作簿。

### 2. 审题落实到真实原件与逐问需求地图

复用 Module 01 的 `requirement_map`、`problem_contract`、附件清单和 risks。每个会影响答案的输入或限制记录可定位出处，例如题面页码和段落、附件文件及表／字段。明确区分题面直接规定、从已知条件推导、仍未解决。查看附件数据单位、空值和表注，核清给定量、决策量和输出、依赖类型。缺页、表格未取得或会改变结论的冲突保留原有 `pending`。后续重述再次对照原文并闭合要点。

先用同一份带陷阱的双问题验证审题产物，再检查是否正确冻结并进入模型。正例应抓住末页限定词、表注单位和前问依赖；删除末页或替换附件造成关键矛盾时应暴露缺口。程序优先检查可客观验证的覆盖与身份，语义正确性由独立核对判断。

### 3. 代码规范落实到实际交付

先用正常入口复现差异，再决定是否需要调整读取选择、交付检查或产物对照。正式动作确认当前小问、项目后端、阶段和批准语义，再取本阶段完整主规则、工程合同和对应模板。把生成结果与合法数据入口、配置、批准公式／约束和预期输出逐项对照。Python／MATLAB starter 提供接口和工作簿骨架，实例需替换为本题真实输入、公式与质量判据。执行当前适用校验并保留实际结果、检查的源文件身份和覆盖范围。若真实样本里的缺陷属于告警或规则盲区，按影响另评估具体规则的改动。

预处理、主求解、结果深化使用各自的正常入口；绘图另核证据链。新验收必须通过现有批准与等待点。Python 和 MATLAB 各取一个合法样例及反例，覆盖错误数据入口、主分析混写、擅改运行配置、阻断级静态错误、仅告警、原生工具缺失，以及“静态检查可过但公式或单位错”。数学语义案例用人工事先冻结的正确要求判定。

### 4. 修复混合绘图

先用三路输入复现混合图：自然语言、单一明确绘图意图、两个显式图意图。修正发生漏选的那层，复用两类现有读集和条件定义。验证混合任务实际读到机理和结果图标准、实表读取及两套 QA；纯机理、纯结果和否定另一图的用例走对应边界。结果图依靠实际已验收工作簿和适用分析。

### 5. 试行正式阶段主规则全文

在最小缺口修复并复验后，先试行**当前正式动作的主规则全文**。覆盖审题、建模、求解／深化、新图、正式写作和审查。写作仍依当前章节和逐问能力预检取源；初审消费入口和共用规则，终审再取终稿专属规则。按实际条件取命题、伪代码、复杂推导和具体图形材料。对已批准的纯配色等明确局部动作保留选段并核对适用证据。优先证明对读漏和成果行为有改善，再决定默认范围。

### 6. 核对阶段覆盖并做宿主对照

复用 `validate_chunk_coverage`，让调用方按当前阶段、问／章、来源身份与项目快照累计必需行范围。全文件以原件 1 至末行为准，选段包含必要父级语境；生效条件也进入核对。缺段主动补读，未裁决条件或取不到的来源标记具体缺口。对不同提交、截断尾段、同样行数但正文错误、状态变更和换问重用失效记录各有反例。

可执行环境使用现有解析器和正文工具试点。仅 GitHub 连接器时由助手按固定提交分段核实，导航只给出原文定位。若要在返回正文、上下文保留和后续写入之间施加强制顺序，需另验证真实宿主能否控制这些动作。阶段报告可以证实收到的正文范围，成果仍须对照规则和项目证据。

## 5. 业务验收与停止条件

| 场景 | 必须观察到的结果 |
|---|---|
| 末页限定词＋附件表注 | 逐问需求地图正确记录限定词、单位、出处、原始对象与依赖。缺关键页保持 pending |
| 跨问恢复与整篇终审 | 取得当前框架所需正文，引用真实上游依赖；旧摘要与当前材料冲突时据当前原件处置 |
| 代码交付对照 | 正确区分后端、阶段、配置、源码和合法数据源；实际检查绑定当前文件；报告告警、阻断和原生覆盖；错误目标方向或单位在成果对照中暴露 |
| 混合图与局部改配色 | 两类图资料在混合任务中齐备；现有纯机理独立路径可继续；已批准的纯颜色调整保持原数值与对象语义 |
| 逐问写作或复核 | 读到当前章实际要求，按事实激活证明和算法；无合格证据时削弱或保留未知结论 |
| 长源截断、状态变更、条件未知 | 对所需范围未覆盖、错版本、项目变化、待裁决条件分别给出可复查缺口。正文返回结论与交付资格分别记录 |

机器验收看现有 resolver、正文提取、校验器和业务路径的正反例。真实会话验收使用脱敏题目和同一项目快照，分别开干净的基线和候选会话，尽量保持模型、指令、工具权限和停止点一致。留存实际返回、发生时序和成果；让独立审阅者按预先固定的题意、数学、代码、证据和审批清单核对。统计实际缺项、工具调用量和耗时。真实上下文压缩、内部 Token 或模型构建号无法观察时按未观测记录。规划字节和有限样本分开报告。

通过标准：明确适用的来源及范围都能核对；失败对照能被识别；现有业务暂停、回执和状态传播可复验；基线中的具体漏读或成果错误有成对证据说明候选解决了什么。出现未解释的交付资格扩大、数值／模型语义退化、新旧项目兼容退化或宿主收益依据不足时，保持试点并复核对应工作包。 [现行读取协议](https://github.com/Vexushi1/mathmodel-skill/blob/4f765d3e1326d3ca7555933059e9313f99b86347/core/runtime_assurance_contract.yaml#L315-L371) · [原有真实会话试验边界](stage_reading_p4_validation.md#5-chatgptgithub-受控试用)
