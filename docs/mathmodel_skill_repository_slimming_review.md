## 哪些工程改动值得单独提出

以下各项保有各自的故障样例或等价性判据。纯函数的复用收益按重复实现、I/O 或行为缺陷衡量；未把程序行数折算为对话 token。具体源码定位与既有测试可从[逐文件记录](mathmodel_skill_disclaimer_cutlist.md)核对。

| 议题 | 已观察事实 | 一项改动可采用的验收证据 |
|---|---|---|
| 框架生成与求解模板联用 | 原初始化入口生成的 compact、full 框架都使用 Markdown 粗体。正常 Q1 标题传入 `PipelineConfig.validate` 后，当前有效版本声明仍被判缺失。 | 实际初始化产物能走到求解配置校验。错误的小问编号、过期状态、框架哈希失配继续有独立负例。 |
| 停止证据和论文入口 | 合成工作簿经过主求解组表后丢失已登记的“执行停止证据”，直接交现有写入器可以写入；另一条独立调用中，空 State 的默认 LaTeX 主文件发现会在空策略处出错。 | 分开修复。前一项从组表写入并读回，核对自适应求解的实际停止点；后一项覆盖无策略、显式选中主文件、错路径和缺文件。 |
| Python 源码静态检查 | 六行样本只改 UTF-8 BOM，CLI 给出的正式缺项相同，但警告由 2 条变为 0，指标变空。两次分析使用了不同解码方式。 | 同次分析复用一次读取、一次解码得到的完整报告；普通 UTF-8 与 BOM 获得相同发现和指标，提交前仍复核实际源件指纹。 |
| 框架章节指纹 | `scripts/validate_project_state.py` 与 `scripts/artifact_fingerprint.py` 分别实现标题匹配、嵌套截断和换行归一。原调查的 8 组独立输入得到相同摘要或缺段结果。 | 让前者复用已有 `framework_section_hash`；用固定预期覆盖 LF/CRLF/CR、嵌套、旧标题首匹配、缺段及缺文件。各消费者在原有时点取得当前源件。 |
| draw.io 的 YAML 加载 | `scripts/validate_drawio_figure.py` 已依赖生成模块。两份加载函数对映射、非映射、坏 YAML、无效 UTF-8、缺文件的结果或异常信息一致。 | 可复用已有 `load_spec`。维持 BOM 与错误诊断、生成 XML 的稳定性、`--check` 的只读行为、实际 XML 几何检查、渲染预览和人工语义审查。CLI 内部重复 `validate_spec` 可另测。 |
| 其它小型重复 | 两个回执入口在 28 组手列用例中识别出相同的 1.5.0 TeX/DOCX 载体；两份 TeX 转义谓词在 51 组输入上结果一致。五份 starter 另各有 7 行相同的 `capabilities()`。 | 优先复用已有依赖；旧/错协议、坏路径、转义和 verbatim 需有反例。每份 starter 保持可独立分发，公共提取须保留独立返回字典及各题型的质量钩子。布尔词表与阶段词汇只在有合适宿主和确定需求时再归并。 |

## 需要新证据的设计问题

- **仓库维护与论文审查的分流。** 在调查基线上、没有比赛项目目录时，以 `maintenance` 和“审查仓库”调用业务 resolver，可返回 `scoped` 开场和论文 `review_report` 计划，含 16 项 `read_now`、8 项缺失前提、正式门为空；同一事件配“整理仓库的重复内容”返回 `no workflow intent resolved`。维护任务已有 `core/bootstrap.yaml#repository_maintenance` 和治理入口。后续如修入口说明，可先验证调用方能否正确分流，同时观察真实论文审查的显式意图与原门序。这个探针仅涉及请求对象的识别。
- **框架和文档的篇幅。** 调查基线的默认实例中，compact 为 398 行、20,920 字节，full 为 653 行、38,378 字节。若考虑改章节或字段，应保留批准身份、题号锚点、既有项目恢复和 compact 扩为 full 时的内容；只在对应条件命中时触发 03B。P30/P31 的两处窄改只覆盖所列原句。README 发布叙述可从维护导航评估，现有历史结案记录和客户端证据范围各有独立用途。
- **历史投影和草稿 CI。** 调查基线有 9 个相邻的版本投影函数；草稿专项命令显式列出 143 个不同测试模块。重排清单、参数化历史比较器或按路径选测各是独立议题。需要稳定的错误样例、逐版本预期和实测耗时。保留跨组及未知改动的原有覆盖、正式 head 的全量发现及适用平台作业。测试预期由独立样本给出。维护资料出现的旧启动指令可标出结案位置，生成分卷和索引继续由现有工作流更新。

## 如何判断精简是否损害建模能力

| 后续变更触及的范围 | 对照旧版与候选版时观察什么 |
|---|---|
| Resolver 与读取 | assured / legacy 双入口、显式意图和显式题号；来源与父段、`unknown` 及条件补读；同 SHA 跨问、换章、换图重新取得原文。对照 `pre_delivery_gates` 的完整顺序、作用域、命令、参数、输入绑定及暂停原因。 |
| 身份、范围与执行 | 独立模型双审、当次 revision 和已验证身份的显式批准；用户实际执行数值代码并交回产物；必要上游缺失按原合同诊断或阻断，独立小问可继续。证据取得、事务写入前的复查和 typed stale 传播分别检验。 |
| 数学和论文成果 | 同题同附件对照题意、单位、约束、跨问依赖、充分化简与求解前提；核对工作簿资格和 03B 的触发理由、逐图证据、关键推导和结论强度。正式 PDF 仍按实际逐页审阅记录判断。 |

调查基线曾定向运行 6 个模块中的 13 项原测试，13 项通过。后续在 W2 合并提交上模拟最终 91 处拟文时，32 个 resolver 场景的所比字段一致，149 个正式来源均能从 129 个生成分卷还原；同组原生回归在原件和最终候选上分别为 91/91。一次试改 124 条时，来源迁移组只通过 15/28，这一反例是撤回越界改写的依据之一。各组覆盖重叠，分别报告。上述记录没有运行这里提出的工程改造，也没有用竞赛成品或真实客户端验证质量提升。

按同一编码器计算，最终 91 条若逐项按拟文实施，一次完整正式正文预计从 342,665 降到 341,483 token，净省 1,182（约 0.345%）。每阶段实际加载的来源不同。原始文本扫描的 1,481 次关键词命中可用于找段落，不能据此推算删除比例、运行性能或模型质量。正式实施以届时实际主题、固定源及 GitHub 工作流的验证结果为准。
