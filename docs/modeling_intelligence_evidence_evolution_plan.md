### 1.1 本次不是从零补四套系统

定向读取实际基线后，必须修正“现有仓库没有双向检查、主张治理、独立审查”的过宽说法。

|---|---|---|

| Claim-Evidence | `claim_strength_calibration`、`analysis_evidence_disposition`、Numeric Profile、Title Claim、Citation Evidence、Paper Fragment 已存在 | 通用主张 ID 与证据选择器、有限派生计算、机器关联和精确影响定位 |
| Independent Review | `model_approval_contract.yaml` 已有独立 reviewer / devil's-advocate 两轮及无原生子代理时的分开审查规则 | 记录实际执行方式、被审快照、证据、未覆盖项、修复复验与回执失效 |
| Case Memory | 已有题型 Packs、模型设计流程、框架项目记忆与模板 | 跨项目的、经审核的结构化决策案例检索；不是替换当前项目记忆 |

依据：基线证据 B03—B08。这里的结论是定向审阅所得，不是全仓实现完备性证明；A0 阶段仍需追踪相关读写入口、测试和潜在重复定义。

### 1.2 四项改造分别回答的问题

- **双向一致性：** 当前实际源码实现的数学对象，是否与已批准模型相符？
- **主张证据关联：** 正文、摘要、图表中的关键论断具体由什么当前证据支持？
- **审查回执：** 谁以什么实际独立程度、检查了哪个版本、发现什么、哪些尚未核验？
- **案例记忆：** 历史结构相似问题中的哪些决策经验值得在本题重新检验？

前三项补可信链，第四项补经验检索。它们都不能替代题面、人工模型批准、实际计算、数值有效性检验或论文渲染。

## 4. 必须保持的系统不变量

以下是不允许在实现中被弱化的边界。

1. `core/bootstrap.yaml` 只做入口指针与启动约定，不重复业务合同。
2. 路由和有序 `pre_delivery_gates` 仍由现有 resolver / router 体系决定，新模块不得私设另一条正式交付链。
3. 当前数学语义仍以框架中的有效 SIB 及现有 semantic identity 机制为准；不新增独立的 `model_identity_hash` 作为第二批准根。
4. `current = validated = approved` identity 的批准规则不被新检查、案例命中或审查回执替代。
5. 普通代码变化首先影响实现和证据新鲜度；只有确认数学语义改变后，才走现有语义变更与批准失效流程。
6. `accepted workbook` 继续是具体计算事实源；主张登记不得成为第二份可以手工修改的数值数据库。
7. 主求解内在数值有效性与 accepted 后的参数/结构/场景稳健性仍分开；不能把所有主张检验塞进 PQS。
8. `Analysis Necessity Gate = not_required` 仍允许存在；它不等于已经验证稳健性。
9. Python/MATLAB 项目后端、源码依赖身份、RUN_CONFIG/RUN_RECEIPT 和用户执行所有权保持现有职责。
10. 状态转移计算保持纯函数/无文件 I/O；文件写入经现有 transaction 协调，校验命令默认只读。
11. 读取、验收和落盘使用一致快照与 read set；不能先核验旧文件、再给已变化的新文件写 PASS。
12. 新模块的 `unknown`、`unsupported`、`not_assessed`、`blocked` 不得自动折叠为通过。
13. 发现证据不足不等于已证明错误；只有明确违反或冲突才判为失败。
14. 确定性脚本、语义审查、真实运行、渲染检查分别记证据，不能相互冒充。
15. 结构化记录可保存人工裁决，但记录存在不证明裁决正确，更不证明任意数学命题或程序等价。
16. 案例内容、外部 README、论文文字均为不可信输入，不具有执行指令或模型批准权限。
17. 历史项目保持只读兼容；没有新字段不追认新资格，有部分新字段时不能回退旧宽松路径。
18. 每个规则只有一个 Authority；project state 管机器状态，框架管当前语义与导航，报告仅是派生视图。

这些边界来自既有 bootstrap、model approval、state transition、runtime assurance 和 writing reasoning 的职责划分，详见 B01、B03、B05、B08—B11。

## 6. 模块 A：Code ↔ Model 双向一致性

### 6.1 问题与增益

已有闭环表解决“应该检查什么”，但不等于已经机器核验所有实现。新增机制重点是：将已批准模型中的关键数学对象映射到**当前真实实现依赖**，再从实现反查重要目标、约束、状态更新和数据变换是否在模型中有依据。

正向关系：

```text
题目要求/模型条目 → Formula/Algorithm Trace → 实现文件与函数 → 结果或检验证据
```

反向关系：

```text
实际实现的关键数学操作 → 对应模型条目或合法数值近似 → 未登记项/冲突/审查结论
```

函数锚点存在、函数名包含 constraint、源码语法通过，均不足以证明约束真的参与求解。

### 6.2 检查对象与差异分类

| 类别 | 例子 | 处置 |
|---|---|---|
| 明确模型不一致 | Robin 边界被直接赋值边界替代；必需约束完全遗漏 | 阻断该实现资格，修代码或回到模型设计 |
| 数值实现选择 | 合法离散格式、容差、初始化、近似求解 | 检查是否在已批准范围/PQS 中；不能一律当作新数学模型 |
| 等价变换 | 变量消元、单位换算、已论证的等价重参数化 | 保存变换依据，不因符号不同自动失败 |
| 经批准的近似 | 受控降阶或代理求解，有误差边界与适用范围 | 标明近似而非严格等价；检查相应证据 |
| 纯工程变化 | 注释、拆函数、路径组织变化 | 更新实现身份并按现有规则重新验收；不自动撤销数学批准 |
| 尚不能判断 | 动态生成约束、第三方黑箱、MATLAB 静态解析不支持 | 明确未核验部分并送语义/运行审查，不能伪造 PASS |

**罚函数不是自动判错条件。** 硬约束问题可以使用罚函数、增广拉格朗日等算法求解；需要检查原始可行域是否保留、最终解是否满足原约束、算法使用条件是否成立。只有把罚函数近优结果当作原问题的合格解，或实际改变可行域/目标而未说明，才构成相应缺陷。

### 6.3 拟议记录内容

每条记录至少包括：关联 ID、小问、primary/analysis 阶段、模型条目/Formula/Algorithm ID、数学作用、真实代码定位、所属 source bundle、预期行为、检查方式、检查证据、结论与未覆盖项。

记录引用现有 `semantic_revision`、`semantic_identity_hash` 和当前实现 bundle，不新造另一套模型批准 hash。源码定位优先“文件＋符号/函数＋内容摘要”；行号仅辅助定位，不能作为身份。

关键数学作用至少覆盖当前任务实际存在的：变量域、目标/损失、约束、初边值、状态更新、参数估计、数据选择/预处理、停止条件、结果指标。不存在的类型记录不适用理由，不制造空模板。

### 6.4 三级核验，不混称“自动等价证明”

1. **确定性结构核验：** ID 唯一、引用可解析、真实函数/模块存在、bundle 一致、必需登记项覆盖、悬空引用和状态冲突。
2. **有限可执行核验：** 针对有明确参考的最小合成实例、边界条件、可行性、单位换算、变形关系进行测试；不能把有限测试当普遍正确性证明。
3. **语义核验：** 对方程、更新逻辑、约束启用、近似合法性和外部求解器调用作独立对照。保存理由和未核验范围，不能只保存布尔值。

Python 可对静态可解析区域使用 AST；MATLAB 优先复用现有 `matlab_code_checks.py` 和真实 Code Analyzer 能力。没有 MATLAB 时保留静态结果与未执行状态，不把 Python 检查冒充 MATLAB 执行。

### 6.5 插入时点与防循环依赖

- 代码正式交付前：已有模型批准仍是前提；核验当前生成代码的结构及关键语义。不能要求尚未产生的 accepted workbook。
- 用户运行后、结果验收时：把 returned receipt 对应的真实 bundle 与已核验实现匹配，追加已有运行证据核对。
- 论文前：已有 Formula/Algorithm Trace 与已执行实现一致；不因论文换一种数学表达就自动要求重新求解。
- 发现语义偏差：首先分类。可以修代码恢复已批准模型时，不改模型；确需改模型时走现有 semantic change→challenge→human approval→重新交付，不让核验器直接改 SIB。

### 6.6 A 模块验收

| 测试 ID | 反例/场景 | 预期 |
|---|---|---|
| A01 | 关键约束有文字记录但无有效实现锚点 | 不能给完整一致性通过 |
| A02 | 实际实现新增决定结果的截断/裁剪 | 提示未登记数学操作，要求判断其必要性与合法性 |
| A03 | 主脚本未变、声明的 helper 改变 | bundle 变化导致旧核验不再适用 |
| A04 | Robin→Dirichlet 边界替换 | 受控样例中确定检出并阻断 |
| A05 | 合法单位变换或等价变量消元 | 有证据时通过，不误判为模型更换 |
| A06 | 已批准近似和严格等价混淆 | 不允许把近似写成严格等价 |
| A07 | 合法罚函数算法＋原约束复核 | 不因使用罚函数名称直接失败 |

| A12 | 核验中源码被另一写入者改变 | read-set 冲突，不能写入过期结论 |

## 7. 模块 B：Claim-Evidence Graph

### 7.1 问题与增益

现有 Claim Strength 和 Paper Fragment 不应重做。新增部分把“有来源”的要求转化为可解析关系：同一关键指标在摘要、正文、表格和图注出现时，能定位到相同当前事实与对应适用范围；来源变化时输出受影响主张和 fragment，而不是靠人工全篇猜测。

必须区分：**来源定位正确、派生算术正确、语义支持充分**。三者不能互相替代。

### 7.2 节点与关系

节点采用现有对象引用，不复制内容：题目/附件事实、已批准模型条目、实现身份、运行证据、accepted 工作簿指标、公式/命题、主张、图表、paper fragment、已核验外部来源。

首批关系限定为：`derived_from`、`supports`、`contradicts`、`qualifies`、`consumed_by`。关系方向、允许的起止类型和唯一性由合同定义。

派生计算图必须无环；不能让主张 A 通过主张 B 又反过来证明 A。现实系统中的反馈或联立方程由一个已验证计算对象表达，不能据此允许证据自证环。

### 7.3 主张最小信息

每条关键主张包含：稳定 `claim_id`、小问/全局范围、事实/计算/比较/机制/稳健性/最优性等类型、文本来源锚点、对象和适用域、关联 Numeric/Title/Formula ID、证据引用、证据处置、消费 fragment、核验范围、未解决项和当前适用状态。

“主张 ID 稳定”不等于“含义可任意改变”。修改对象、比较基准、适用域、单位或因果含义后，应生成修订并使旧证据关联等待复核。只修改标点或允许的显示名称，则按现有写作语义规则处理。

关键主张优先覆盖题目直接答案、摘要数字、核心比较、标题贡献、最优性/稳健性/因果类强断言。初版不要求登记所有背景句、坐标刻度和普通连接句。

### 7.4 工作簿证据选择器

优先选择：

```yaml
# 仅为拟议协议示例，所有名称和值均为合成示例。
artifact_role: accepted_solution_workbook
question: Q1
stage: primary
selector:
  sheet: 示例结果
  row_key:
    scenario_id: baseline
    metric_id: completion_time
  value_column: value
  unit_column: unit
  expected_cardinality: 1
```

强制要求：

- 用实际题目/现有 workbook schema 解析工作表和表头，不强加新工作簿格式。
- 记录/核对场景、样本范围、时间点、指标定义和统计量身份；同名指标不自动等价。
- 行键重复、多结果、零结果、表头歧义、单位冲突均不能猜选第一行。
- 单元格坐标可用于题目固定模板，但必须附模板身份/版本及对应行列语义；`B12` 不能独自代表一个指标。
- 工作簿中的公式单元格不能因保存了公式字符串就被当作已计算值；缓存缺失、外部链接或计算状态未知时标记待复核，不启动电子表格应用替用户重算。
- 有限值、区间、分类值按类型检查；不能对所有证据强制“浮点数”。
- 选择器解析必须复用现有 accepted qualification；hash 不一致的文件不能因目标单元格看似相同而继续当 accepted。

### 7.5 有限派生操作

只允许有类型和边界的白名单操作，例如：差值、比值、相对变化、百分比/百分点换算、显式单位换算，以及已声明轴/集合上的有限汇总。禁止 `eval`、任意 Python 片段、网络请求或隐藏求解器调用。

示例：合成数据中 baseline=100、candidate=80，改善比例为 `(100-80)/100=0.20`。必须同时记录“越小越好”的方向和比较范围；不能把 20% 写成 20 个百分点。

这种派生核验属于**证据复核**，不等于再次执行赛题模型。不得在派生操作中重拟合、重优化、补齐缺失实验或生成未存在的敏感性序列。

展示精度继续服从 Numeric Profile。不能为了字符串一致强行统一两位小数，也不能只比较显示后的四舍五入值。

### 7.6 主张强度与否证处置

直接消费既有 `core/writing_reasoning_contract.yaml#claim_strength_calibration` 与 `#analysis_evidence_disposition`，不复制一套证据等级。

- “相对某基线改善”需要匹配的比较对象、指标、样本和真实结果。
- “稳健”必须有范围和保持的结论；没有独立深化证据时只能报告当前计算世界。
- “全局最优”需要与该项目一致的可核验证书或严格证明；启发式最好值、多个算法相近不能替代。
- “显著”必须对应已有统计或预定义实践阈值；脚本不自行发明检验。
- “机制主导/因果导致”不能由单一数值相关或一组情景差值自动升级。
- `modify/reject` 应指出影响的是核心答案、模型成立性还是辅助措辞。辅助措辞可删除/限定时，不自动触发全题重算；核心答案被否定则必须回到适当阶段。

### 7.7 新鲜度与写作更新

精细主张依赖用于**增加定位能力**，不能抵消现有 artifact-level stale。

```text
文件变化
 → 原有 accepted / artifact assurance 先判定资格
 → 相关证据引用待重新核验
 → 主张和 fragment 输出影响路径
 → 原始事实重新合格后，才判定哪些主张可以复用
```

例如工作簿只做了行重排：完整文件身份已变化，仍须先满足现有重新验收要求；之后若语义选择器和所选值/单位/范围均一致，才可复用相应主张的语义支持，不能倒过来跳过数值来源验收。

初版保守失效优先；没有经过专门测试的“语义内容 hash 不变所以免复验”不得上线。局部刷新仍需重新生成最终 source/PDF/package 的既有 attestation。

| 测试 ID | 场景 | 预期 |
|---|---|---|
| B01 | 摘要与正文使用同一指标却值不同 | 定位到具体 claim/fragment |
| B02 | 比较基准与候选交换 | 不接受方向错误的改善率 |
| B03 | 相对百分比与百分点混用 | 根据类型和定义报冲突 |

## 8. 模块 C：Independent Reviewer Receipt

### 8.1 问题与增益

既有审查规则已经要求两轮独立判断。新增回执的价值在于把“我检查过”变成：检查对象、快照、方式、证据、发现、未覆盖项和复验状态可被追踪。

回执不是数学正确性证明，不是不可伪造签名，也不是额外人工批准。

### 8.2 独立性必须按实际能力记录

| 执行方式 | 可以声称 | 不能声称 |
|---|---|---|
| 原生独立会话/子代理，有宿主可核对的执行记录 | 对特定输入做了独立会话审查 | 与作者错误统计独立、绝不受同模型偏差影响 |
| 人工审阅，有可核对记录 | 指定人工审阅者检查过该快照 | 人工未查到的部分也通过 |
| 同一助手按既有合同分开两轮审查 | 已完成分离的双轮审查 | 原生子代理独立执行或外部人工验收 |
| 作者自检 | 完成作者自检 | 完成独立审查 |
| 无执行证据或身份无法验证 | 仅为声明/待核验 | verified independent |

协议可拟用 `native_isolated`、`human_review`、`separated_passes`、`author_self_check`、`unverified` 等方式标签，但最终枚举由 C1 冻结。`independent: true` 不能自行提高证据等级。

沿用当前无原生子代理时可分开审查的规则；本计划不将“没有子代理”自动改成所有任务阻塞。若未来某特定高风险门要求更强独立性，必须另有明确规则与兼容设计。

### 8.3 最小回执字段

包含：`review_id`、协议版本、门禁/角色、小问和对象范围、输入清单、语义 identity 引用、代码 bundle/工作簿/正文等适用身份、审查准则版本、实际执行方式、执行来源、实际运行命令和退出码（若有）、检查项目、发现 ID、严重度、证据定位、未覆盖项、结论、所替代回执及复验关系。

字段按阶段适用：模型审查不能要求尚未产生的工作簿或论文；纯排版审查不能宣称检查了模型正确性；数值审查不能用 PDF 可编译代替。

### 8.4 快照绑定与自引用规避

- 回执绑定明确的被审输入集合与相应 authority fingerprint，不只绑定一个笼统项目版本号。
- `state_generation` 可作为读取/写入一致性的上下文，但无关状态更新不必使所有语义审查自动过期；适用性以合同确定的输入依赖为准。
- 不直接把“包含回执自身的完整 state 文件 hash”作为该回执的固定身份，否则每写一次回执就会自我失效。
- 被审对象集合、规范版本和内容摘要应有稳定排序、明确规范化及 domain separation；不能排除真正影响结论的依赖。
- 回执 hash 只能检查记录完整性。能同时修改记录和 hash 的同一主体仍可能伪造，因此必须区分自声明、宿主记录与可核对外部来源。
- 原生执行证据不可用时如实降为相应方式，不以手填 run ID 伪装宿主证明。

### 8.5 结论、适用性与问题闭环分开

建议分别表示：

```text
审查结论：pass / fail / inconclusive
当前适用性：current / stale / superseded / unverified
执行能力：实际支持的独立性方式
问题闭环：open / corrected / reverified / not_applicable
```

最终是否允许进入某阶段，仍由现有门禁消费这些事实决定。`pass + stale` 不能作为当前通过；`inconclusive` 不能被忽略；关键问题不能仅因作者标注 corrected 就算关闭，必须有对应复验。

局部复验只覆盖已列对象；未检查部分不得重新签成全量通过。同一根因保留稳定 finding ID，避免重复扣分和遗漏。

### 8.6 不允许自动触发的行为

回执校验器不得修改源码、重写模型、接受工作簿、批准后端迁移、批准数学模型、自动删改论文主张或合并仓库 PR。其输出是现有 writer/gate 的输入，不是无限权限执行器。

### 8.7 C 模块验收

| 测试 ID | 场景 | 预期 |
|---|---|---|
| C01 | 自检填 independent=true | 不提升为已核验独立执行 |
| C02 | 旧输入的 PASS 重放给新输入 | stale/不适用 |
| C03 | 审查准则或适用 Authority 改变 | 要求按影响范围复核 |
| C04 | 两轮使用同一 verdict 复制为不同角色 | 不能仅凭两条记录证明独立完成 |
| C05 | 无原生子代理但真实完成分开审查 | 保留现有可用路径，准确标注方式 |
| C06 | 修正代码后只有作者勾选 corrected | 关键发现仍需复验 |
| C07 | 局部复验冒充全量检查 | 拒绝扩大范围 |
| C08 | 写入回执导致其自己的 hash 永久变化 | 自引用反例必须被设计和测试排除 |
| C09 | 审查快照读取后对象变化 | 不能提交过期回执 |
| C10 | failed/unknown 的命令被写成已运行成功 | 与真实执行证据冲突时拒绝 |
| C11 | 未完成数值检查但声称已复现 | 不给予相应复现资格 |
| C12 | review PASS 尝试代替 Human Model Approval | 现有批准门继续阻断 |

## 9. 模块 D：Case Memory

### 9.1 问题与增益

Case Memory 保存“为什么选、为什么不用、需要什么数据、怎么验证、哪里失败”的决策经验。它不保存一个可以直接套用到新题的获奖答案。

检索目标是结构相似：任务目标、数据制度、变量类型、约束、时间/空间/网络依赖、不确定性与验证需求。题名相似或同一个模型名称只能是弱线索。

### 9.2 准入与分层

| 状态 | 用途 | 限制 |
|---|---|---|
| `draft` | 待整理的内部候选 | 不进入正式推荐索引 |
| `quarantined` | 来源、许可、隐私、抽取或事实存在疑问 | 不向模型设计提供推荐依据 |
| `reviewed` | 有完整来源、逐项证据和迁移边界 | 仍只是建议，不授权模型 |
| `retired` | 已发现问题或撤回 | 不再推荐；保留撤回原因及引用影响 |

区分 `observed_in_source`、`curator_inference`、`recommended_validation`、`synthetic_example`。没有在原论文中看到的基线、消融和失败方案，不能补写成原作者做过。

### 9.3 案例最小字段

- 身份：case ID、来源版本/固定提交或内容 hash、作者/年份/比赛来源（能核实时才填）。
- 权利与隐私：许可标识/来源、允许用途、署名要求、公开性、授权依据、敏感内容检查。
- 结构：任务类型、观察单位、样本制度、变量/约束/目标、时间/空间/网络、依赖链、不确定性。
- 决策：经典基线、实际采用模型、已记录替代方案、选择理由、失败风险和实现代价。
- 验证：实际完成的检查、结果证据范围、未完成部分、条件性结论。
- 迁移：可复用模式、不能直接迁移的参数/阈值/地区/几何/数据口径。
- 锚点：原始文件位置、页码/章节/函数、抽取方式、人工复核范围、OCR/解析局限。
- 状态：审核者与时间、版本、准入/撤回理由。

严禁为了 schema“非空”而伪造替代模型或验证记录；允许明确缺失，并按重要性决定隔离或有限使用。

### 9.4 来源与许可边界

当前任务只授权编写计划，不授权把用户跨聊天材料、论文、数据、对话、路径或运行记录发布到公开仓库。将来任何真实项目入库必须单独确认公开范围并去除个人、学校、账号、绝对路径等敏感信息。

外部仓库公开可见不等于允许自由复制、修改和再分发；代码许可、论文许可、数据许可和模板许可需分别核对。无清楚许可或含非商业/相同方式共享/专有内容时，不自动导入；优先保存经审查的最小索引与链接，不能默认改写摘要就消除了全部权利限制。一般说明参考 GitHub 官方许可文档 B16；具体疑问保留为待授权事项。

不分享或迁入本地字体文件，不批量搬运第三方字典，不删除原有署名或声明。

### 9.5 检索实现

首版使用可离线运行的确定性词项/字段加权检索，保留经典检索基线；不把 embedding、reranker、网络 API 或新数据库设为前置依赖。

建议流程：

```text
当前 Problem Contract 的结构特征
 → 许可/状态/用途硬过滤
 → 分任务及全链检索
 → 去重与同源聚类
 → 有界排序
 → 返回少量案例、匹配理由、差异与禁迁移项
 → 当前模型设计重新判断采用/拒绝
```

检索分数不是“模型适用概率”或“获奖概率”。没有足够证据可以返回零匹配。历史同题及其改写需归为同源组，不能用多个 fork 制造多源印证。

缓存键包含语料版本、结构化查询、检索器版本和过滤配置。案例撤回后缓存失效；不得复用旧命中绕过撤回。

### 9.6 写入与学习机制

不允许“做完一次题就自动学入公共库”。候选案例必须依次经过整理、来源/权利审查、事实审查、迁移边界审查和明确入库操作。

案例建议被本题采用时，只在当前决策记录中保存 case ID/版本、采用部分、拒绝部分和本题证据。若改变当前模型，必须正常走模型设计和批准；case 引用本身不能写入 approved 字段。

后续案例被撤回时，应把相关当前项目引用列为待复查；不能自动认定所有历史数值错误。已独立由本题证据支持的部分可以经复核保留。

### 9.7 试点与评价

先用少量、跨结构的合成/明确授权案例验证闭环，再扩充真实案例。初始规模不是能力指标；不为达到 139、5713 等外部数字牺牲证据质量。

至少覆盖预测、评价、约束优化、机理/动力学、网络或调度、随机仿真、跨问混合链中的代表结构，并包含不应迁移的反例。

评价时将同一道题、同源论文和近重复案例放在同一分组，避免检索库已经包含测试题答案。比较“无案例记忆”“词项基线”“结构化检索”在同一固定任务集上的适配性、错误推荐、必要条件识别、上下文成本和任务完成质量；不单靠 LLM 自评分证明提升。

## 11. 失效传播矩阵与防自证规则

| 变化 | A 一致性 | B 主张证据 | C 审查回执 | D 案例引用 | 数学批准 |
|---|---|---|---|---|---|
| SIB/语义 revision 实质变化 | 受影响记录过期 | 相关模型/结果主张待复核 | 相关模型与下游审查不适用 | 重新评估所用模式 | 按现有规则 stale |
| 主代码/helper/bundle 改变 | 对应阶段过期 | 原结果资格按现有规则处理 | 被审实现/结果依赖的回执过期 | 通常不变 | 不仅因文件变化自动 stale |
| analysis 代码/工作簿改变 | analysis 范围过期 | 对应 support/modify/reject 待复核 | 相应范围过期 | 通常不变 | 按是否实质改模型判断 |
| 工作簿字节变化 | 运行绑定复核 | 不得绕过 accepted，随后定位受影响主张 | 依赖该工作簿的回执不适用 | 不自动修改案例 | 不自动改批准 |
| 只有论文文字变化 | 数值实现通常不变 | 复核对象/范围/措辞是否变义 | 相应文本审查待复验 | 不变 | 无语义变化则不撤销 |
| 图样式变化 | 不变 | 数值主张通常不变；图文关联核对 | 图视觉与排版审查待复验 | 不变 | 不变 |
| 审查回执自身新增 | 不自动重算模型 | 不自动改变事实 | 不形成自引用 hash 环 | 不变 | 不变 |
| 审查准则版本改变 | 依适用范围复核 | 依新旧规则变化判断 | 记录准则变化及重新适用性 | 不变 | 不自动批准或撤销 |
| 案例/索引更新 | 不直接改变已执行实现 | 不直接改当前数值事实 | 通常不变 | 缓存失效，受影响引用待复查 | 只有采纳并改变语义才进入审批 |

所有新事件必须经过现有状态 Authority 定义，不许在四个脚本中各写一份失效集合。现有保守失效规则在首版保持；缩小失效范围必须另有明确证明和回归测试。

审查、主张和案例的派生关系不能自证：自己的文字不能作为自己的计算证据；同一来源的多个导出不能算多个独立实验；review PASS 不能证明其所引用工作簿已 accepted。

## 13. 版本、兼容与迁移

### 13.1 不预先决定“大版本”

本次不升级 `10.0.1`。未来向后兼容且默认不改变既有资格的可选能力，可评估 minor；默认强制新增 gate、破坏 Schema/CLI/交付约定或拒绝历史有效路径时必须评估 major。不得仅为宣传叫“11.0.0”，也不能把破坏性行为装成 patch。

Skill 版本、Project State Schema 版本、SIB 版本、RUN_RECEIPT 协议、新能力协议分别维护。版本一致性是对应关系正确，不是全仓字符串替换。

### 13.2 三类项目处理

| 项目类别 | 行为 |
|---|---|
| 没有新协议/字段的历史项目，只读审阅 | 按现有能力读取；明确新核验未做，不追认或强制迁移 |
| 历史项目主动进入新协议阶段 | 先 inspect/dry-run、解释影响，再经明确授权建立缺失真实记录 |
| 已有新协议、字段残缺/未知版本/旧回执重放 | 不回退旧宽松逻辑，报告阻塞或待迁移 |

新项目也不能只因升级仓库就获得 approved、accepted 或独立审查资格。

### 13.3 激活策略

按能力和范围显式激活，而非一个布尔值一次启用全部四项。关闭检索不关闭已有批准/数值/写作硬规则；关闭新增能力不能作为已经声明新协议的项目绕过失败项的方式。

最初接入可提供只读观察模式：报告新发现但不伪称所有扩展门已强制执行。正式强制模式上线前必须记录默认行为变化、历史项目影响和版本决策。

### 13.4 迁移安全

迁移不从自由文本自动“恢复”已验证语义，不倒填 reviewer、不重新签旧 hash、不以返回数字相同替代 source bundle 资格。

写入前检查 state generation 与涉及源码、工作簿、规范的 read set。transaction 已 prepared 后的恢复方式必须遵循当前实现；不能笼统承诺所有失败“自动回滚”。遇到 pending journal 应停止/按既有恢复入口处理，而非新 validator 私自恢复。

撤回实现与用户状态迁移是不同动作。回滚仓库代码不能删除用户已有证据或把不支持的新状态伪装成旧格式。

## 14. 测试策略与执行证据

### 14.1 三个层面分开

1. **仓库完整性：** Authority、路径、Schema、生成物、入口和版本。
2. **核验器行为：** 使用独立临时目录中的明确合成正负例验证四项协议。

## 15. 效果与成本评价

### 15.1 正确性指标

- 核验器的误放行率：在已冻结的明确违规 fixture 上，不允许 false accept。
- 合法正例误报：等价变换、允许格式、合法罚函数、旧项目只读等正例须通过或准确标为需要人工核验，不机械拒绝。
- 关联完整性：在人工确认的关键主张集合上，要求全部有解析成功的来源/范围/消费映射；不宣称机器穷尽了任意论文所有语义。
- 失效正确性：应失效项全部失效；不相关数学批准不能因新增回执或案例检索被撤销。
- 证据真实性：执行命令、独立方式、未核验范围和来源资格不能靠填 PASS 绕过。

### 15.2 建模智能指标

Case Memory 的评价包括结构适配性、必要数据条件识别、错误迁移次数、合理 no_match 比例、基线/替代方案质量以及相同预算下的建模结果。固定分组留出集、评分准则和模型/检索器版本后再比较。

小样本人工试点只用于发现问题，不宣称统计稳定提升或获奖提升。LLM judge 可辅助分类，不作为唯一真值；关键争议应回到原始题目与证据裁决。

### 15.3 资源开销

A0 先测现有 resolver、同步、代码交付和写作审计的耗时/加载量。扩展关闭时不得引入案例库、网络依赖或全量读取；开启时按实际受影响对象增量读取。

具体耗时、内存、case 数量和上下文预算在 A0 基线测量后预先冻结，不能看到不利结果后放宽阈值求通过。初版优先小而确定的实现，不以缓存命中掩盖应执行的 freshness 检查。

## 16. 安全、隐私与可维护性

| 风险 | 防护与测试 |
|---|---|
| 记录/hash 自声明冒充真实执行 | 保留证据等级、来源和范围；有 hash 不等于有可信签名 |
| 外部案例提示注入 | 内容仅作为数据，不能改变工具权限、审批规则、读写根 |
| 文件路径越界/符号链接跳出项目 | 复用项目根边界检查，解析后的真实路径须在允许范围 |
| YAML/JSON 或派生表达式执行代码 | 安全解析、有限类型、操作白名单，不使用任意 eval |
| 超大文件/深递归/环导致资源耗尽 | 明确尺寸、深度、节点和读取预算；超限返回限制，不静默截断后通过 |
| 证据来源时点混合 | 绑定同一快照和 read set；scope/样本/场景一致性检查 |
| 案例库吸入私有项目 | 显式公开授权、去标识审查、quarantine；默认禁止跨项目自动收集 |
| schema 与文档双重事实源 | 状态定义唯一；框架/报告为当前语义和机器记录的有限视图 |
| 功能强制导致兼容破坏 | 分能力激活、历史只读、部分新协议 fail closed、版本评审 |
| 为验证而造无用文件 | 复用既有状态/模板/报告；只为真实消费者创建记录 |
| 维护负担超过收益 | 每阶段检视新增 Authority、读写入口和产物数量；无必要的层撤销 |

错误消息应包含：对象 ID、当前范围、期望与实际身份/类型、失败原因、影响对象和可执行修复方向。不得输出 API key、完整私有路径或无关个人信息。

## 18. 后续维护者的执行指南

6. 写出本阶段修改简报和文件白名单；检查重叠 PR 后建立/接管唯一主题分支。
7. 先实现正负例与纯核验，再接入 writer/gate；同一 PR 不混入其他模块重构。

11. 形成审查结论与兼容/回滚说明；满足授权和治理条件后才能合并。
12. 更新本文进度表，填写实际 PR、merge SHA、测试和未完成项，再决定是否进入下一阶段。

中断交接至少记录：当前阶段、branch/head/base、已改文件、已读源、已执行命令与结果、生成物状态、未解决问题、下一条具体动作。不要写“基本完成，继续优化”这种无法恢复的状态。

## 22. 决策摘要

本计划选择的是**稳定现有可信运行时，渐进增强关联、审查和经验检索**，不是重新发明一套 Agent 框架。

最重要的四个验收问题始终是：

1. 实际实现是否符合当前批准的模型，未知部分有没有诚实保留？
2. 论文关键主张是否能回到当前合格证据，论断范围是否越界？
3. 审查是否真实发生、对应哪个版本、修后是否复验？
4. 历史案例是否只是有边界的建议，而没有越权替代本题事实和审批？

**2026-09-25 原编制结论：只形成并提交实施指南，所有功能实施阶段尚未开始。**
