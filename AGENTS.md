# Agent instructions

## Runtime tasks

1. Read `core/bootstrap.yaml` first.
2. Run `scripts/resolve_workflow.py` for one or more intents; do not preload the whole repository.
3. Classify each subproblem with one objective, up to three structures and independent capabilities using `core/task_taxonomy.yaml`.
4. Create or update project-root `模型论文框架.md` after the model is locked; keep only current semantics. Treat it as assistant-readable project memory, not merely a user-facing deliverable: when it exists and is current, read the relevant current-scope/subproblem/dependency/result/figure sections before downstream work instead of reconstructing the model from chat memory; read the full framework for cross-chat recovery, full-paper writing and final review. The framework includes Formula Trace, Algorithm Trace, current writing-governance registries/claims and evidence locations; concrete numerical claims still require accepted-workbook verification, while project state owns hashes and stale status.
5. Before formal model/code/returned-workbook/downstream delivery, run `scripts/validate_semantic_governance.py`; before formal artifact delivery, also run `scripts/sync_project.py <project_root> --write --strict --delivery-scope <scope>` and include `sync_report.yaml`.
6. Semantic governance may accept the current semantic hash and propagate stale but never restores numerical validity. The synchronizer never invents model semantics, results or passed validation; it only discovers artifacts, reads workbook structure, hashes files and propagates stale.
7. Python performs primary solving and adaptive result analysis and writes the two current standard workbooks. MATLAB reads exact unique headers from the same question directory and draws formal figures. LaTeX is the default paper and final-PDF path; DOCX is an explicit optional review branch and is not a LaTeX prerequisite.
8. New projects use `问题X求解结果.xlsx` and `问题X结果深化分析.xlsx`. Historical naming is handled only by dedicated compatibility contracts and must not be generated by active templates.
9. Task-specific solve/result-analysis code is user-executed at full fidelity under `core/user_execution_contract.yaml`; do not run it in the assistant or silently reduce data, grid, horizon, repetitions, tolerance or solver fidelity.
10. Load `packs/artifact/proposition_proof.md` only for explicit proof requests or a nonzero proposition plan. Load `packs/artifact/algorithm_flow.md` for an explicit paper-algorithm request or a writing/review route that must consume a current `stepwise/pseudocode` Algorithm Trace. The complete-deliverable `full_workflow` route may also keep this small Pack in context across its user-execution boundary so later paper stages do not lose the presentation contract; ordinary `full_solution` / `code_and_solution` must not preload it. Plain “算法/求解” remains a numerical-solution intent; do not route it to pseudocode presentation. Do not load `legacy/` by default.
11. When an Algorithm Trace is used, preserve the chain `model/formula/proposition/constraint → paper algorithm → real Python implementation → accepted workbook result/evidence`; machines may check declared fields and anchors but must not infer algorithm correctness or convergence from step text.

## Repository modification tasks

1. Before changing any active repository file, read the current `main` versions of `core/bootstrap.yaml` and `SKILL_CHANGE_GOVERNANCE.md`.
2. Confirm the current Skill version, latest `main` commit, overlapping open PRs and authoritative source files.
3. Produce the required change brief before writing files.
4. Use one dedicated branch and one single-theme PR; never write directly to `main`.
5. Do not rely on previous-chat memory, duplicate authoritative rules, hand-edit generated indexes or falsify test status.
6. Run the governance-mandated lint, full tests, generated-file checks and affected specialist checks before merge.
7. Report branch, PR, merge status, commit SHA, compatibility and unfinished validation accurately.
