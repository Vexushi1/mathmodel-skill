# HSK Core Policy v6.4.1

本文件只保存全局硬规则。任务路由、产物图、分类、输出、工作簿和项目状态分别以 `core/workflow_router.yaml`、`core/module_manifest.yaml`、`core/task_taxonomy.yaml`、`core/output_contract.yaml`、`core/workbook_schema.yaml` 和 `core/project_state.schema.yaml` 为准。

## 1. 总目标与优先级

数学建模任务必须形成可提交、可复现、可解释、可审查、可答辩的闭环。优先级为：

$$
\text{题意正确}>\text{机制与变量闭合}>\text{数据可信}>\text{主求解精度}>\text{结果证据}>\text{图表}>\text{论文表达}>\text{形式创新}.
$$

不能落地、不能解释、不能检验、不能复现的模型必须否决、降级或重构。禁止为了高级模型、统一扰动、算法数量、图表规模或排版炫技偏离题意。

## 2. 启动与按需加载

1. 首先读取 `core/bootstrap.yaml`；
2. 使用 `scripts/resolve_workflow.py` 根据一个或多个用户意图生成确定性执行计划；
3. 只加载命中的模块、题型 Pack、竞赛 Pack、交付 Pack 和必要模板；
4. `legacy/` 不参与默认执行；
5. 不要求在路由前通读整个 Skill、所有模块或全部资产。

## 3. 逐问正交分类

每个小问分别记录一个 `classification.objective`、至多三个 `classification.structures` 和一份顶层 `capabilities`。顶层 capabilities 是唯一权威能力事实源；旧别名仅作兼容派生。

capabilities 决定主结果成立所必需的可行性、残差、离散、收敛、外样本、不确定性、泄漏、校准或可识别性检查。它不等同于后续结果深化分析方法清单。

## 4. 默认工作顺序

```text
审题与数据协议
→ 模型路线比较与模型锁定
→ 创建或重写模型论文框架.md
→ Python完整主求解
→ 主结果质量门
→ 问题X求解结果.xlsx
→ 基于题目、模型、数据和主结果选择结果深化分析
→ 问题X结果深化分析.xlsx
→ MATLAB读取真实工作簿绘图
→ 直接编写并持续修改LaTeX
→ AI模板感清除
→ 编译与终审
```

主求解和结果深化分析语义分离但证据闭环。任务可停止在用户要求的交付物，不得伪造缺失前置结果。DOCX 仅在用户明确要求 Word 审阅、批注、协作或特定提交格式时加载。

## 5. 主求解质量门

主求解阶段必须在当前模型口径下得到尽可能准确、可行、收敛且可复算的结果。以下内容不得移到后续分析：

- 数据字段、单位、时间与空间对齐；
- 求解器状态、停止条件、最优间隙或 KKT 条件；
- 约束违反、均衡、守恒、离散与收敛检查；
- 预测问题的无泄漏切分和基础外样本精度；
- 仿真的随机种子、基础重复次数与区间；
- 参数估计的可识别性和基本统计有效性。

质量报告写入求解工作簿的 `主结果质量门` 工作表。存在未通过项时，状态不得进入 `solved`，也不得启动结果深化分析。

## 6. 结果深化分析

结果深化分析只接受已经通过质量门的主结果。其方法由题目要求、模型结构、数据特征、主结果表现和评委风险触发，可选择：

- 参数与机制敏感性；
- 不确定性传播与场景鲁棒性；
- 多算法、多初值、上下界或数值一致性；
- 模型结构、约束、赋权或分布假设稳健性；
- 异质性与误差分解；
- 阈值、边界与极端情景；
- 外样本、滚动或迁移稳定性。

禁止所有题目统一执行 ±5%、±10% 参数扰动，禁止把随机重复运行自动称为鲁棒性，禁止用后续分析掩盖主结果未收敛、不可行或基础精度不足。

分析工作簿必须包含 `分析设计`、至少一个实质分析工作表和 `结论稳定性汇总`。若分析发现合理变化下结论频繁反转、算法差异显著或结构设定失真，必须标记主结果及下游产物 stale，回退模型设计或主求解并重新计算。

## 7. 当前模型框架与事实源

`locked_model_spec` 形成后，项目根目录必须维护 `模型论文框架.md`，只保留当前有效模型语义、主结果、深化分析结论、命题规划和图表映射。旧版本由 Git 历史保存。

事实源边界：

- 模型语义与论文组织：`模型论文框架.md`；
- 主数值事实：`问题X求解结果.xlsx`；
- 结果解释、稳定范围与失效边界：`问题X结果深化分析.xlsx`；
- 分类、状态、路径、哈希和 stale：`state/project_state.yaml`。

四者冲突时停止下游写作，回到源产物修正。

## 8. 正式交付同步门槛

所有正式模型、代码、工作簿、图表、DOCX、LaTeX 或提交包交付，必须执行：

```bash
python scripts/sync_project.py <project_root> --write --strict --delivery-scope <scope>
```

同步器按 exact scope 检查产物、Schema、MATLAB 引用和分层哈希，只允许设置或保持 stale，不得生成模型语义、伪造结果、提升 `result_quality_status` 或 `result_analysis_status`。

## 9. 软件职责与目录

- Python：数据读取、预处理、主求解、质量门、结果深化分析和中文工作簿；不绘制正式论文图。
- MATLAB：读取同目录真实工作簿绘制正式结果图，不重新计算核心结果。
- LaTeX：从首个正文版本开始直接编写并持续修改，承担终稿与 PDF。
- DOCX：显式按需分支，不是 LaTeX 前置。

```text
项目根目录/
├─ 赛题与附件
├─ 模型论文框架.md
├─ 问题一求解.py
├─ 问题一结果深化分析.py          # 可与求解脚本合并编排，但职责独立
├─ state/project_state.yaml
├─ sync_report.yaml
└─ 结果数据表/问题一/
   ├─ 问题一求解结果.xlsx
   ├─ 问题一结果深化分析.xlsx
   ├─ q1_plot.m
   └─ 图表/
```

## 10. 图表、命题与写作

MATLAB 字段定位采用精确表头唯一匹配，不得模糊匹配或别名猜测。每张图必须绑定工作簿、工作表、真实表头、脚本、正文结论和框架映射。

命题可以为 0，全文最多 4 个；命题必须服务问题简化、模型必要性、降维、约束删减、可行性或理论边界。数值实验不能替代证明。

LaTeX 直接读取当前框架、两类工作簿和已批准图表。正文按题型使用“结果分析”“稳定性分析”“误差分析”等自然标题，不机械保留“敏感性与鲁棒性”固定章节。

## 11. 终审原则

终稿必须核对题意覆盖、模型闭合、主结果质量门、深化分析选择理由、工作簿—MATLAB—图表—正文证据链、编译状态和提交包完整性。没有支撑核心结论的分析和图表应删除，而不是为了完整感保留。
