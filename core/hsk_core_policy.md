# HSK Core Policy v7.2.0

本文件只保存全局硬规则。题意口径、语义闭环和语义变更状态以 `模型论文框架.md`、`core/project_state.schema.yaml` 与 `scripts/validate_semantic_governance.py` 为准；目录与交付文件以 `core/output_contract.yaml` 为准，统一数据预处理以 `core/global_preprocessing_contract.yaml` 为准，用户本地执行与工作簿验收以 `core/user_execution_contract.yaml` 为准，题目专属 Python 工程质量以 `core/code_quality_contract.yaml` 为准。本文件不复制这些合同的完整字段。

## 1. 总目标与优先级

数学建模任务必须形成题意正确、机制闭合、数值可信、可复现和可审查的成果链。优先级为：

$$
\text{题意正确}>\text{语义与机制闭合}>\text{数据可信}>\text{完整版数值求解}>\text{结果证据}>\text{图表}>\text{论文表达}>\text{形式创新}.
$$

不能落地、不能解释、不能检验或不能复现的模型必须否决、降级或重构。运行成功、结果合理、多个算法一致都不能替代题意和模型语义正确性。

## 2. 四项前置语义治理硬规则

### 2.1 Problem Contract：题意口径冻结

进入模型设计前，每问必须冻结研究对象、原始/派生对象、已知/可计算量、决策/状态/输出量、显式/隐含约束、禁止假设、数据角色与小问依赖。不得根据附件呈现方式、已有程序、求解方便性或结果表象反推题意。关键歧义未解决时不得锁模。

### 2.2 题面—数学—代码三层闭环

每个核心对象、条件、变量、目标、约束和输出必须形成：

$$
\text{题面对象与要求}
\rightarrow
\text{数学变量/关系/目标/约束}
\rightarrow
\text{Python变量/函数}
\rightarrow
\text{工作簿输出或验证证据}.
$$

出现“题目要求有、代码没有”“代码有、数学层无来源”“数学关系无题意/机制依据”或单位、粒度、索引含义断裂时，正式代码交付必须停止。

### 2.3 模型语义修改治理

题意解释、数据范围、变量、参数、假设、目标函数、约束、预处理、算法语义或小问依赖发生变化时，必须递增当前小问 `semantic_revision` 并记录变更类别。`模型论文框架.md` 只保留当前有效版本，历史由 Git 保存；不得在项目中另堆多份旧口径。

已验证语义发生变化时，先将本问主结果及全部下游 stale，再按 `depends_on` 的 `data / parameter / model / result` 依赖递归传播到受影响后问。接受新语义哈希不等于恢复旧数值；只有重新求解和验收后才允许恢复数值结果状态。

### 2.4 Complexity Sanity Check

复杂赛题异常退化为低维直接计算、弱耦合独立求解、动态转静态、多主体转单主体，或题目专门条件/附件字段大量闲置、关键约束长期不生效、后问近乎复制前问时，必须触发复审。简化只有在严格等价、可证明降维、题意允许或机制充分时才可接受；否则 `complexity_sanity_status=review_required`，禁止进入主求解。

上述四项由 `scripts/validate_semantic_governance.py` 在正式模型、代码、返回工作簿和下游交付前执行。该门只检查和传播 stale，不运行赛题代码、不生成数值结果，也不清除数值 stale。

## 3. 项目级统一数据预处理

当两个及以上小问共享同一原始数据源、共享同一清洗/单位/坐标/滤波/重采样口径，或用户明确要求统一数据预处理时，正式流程必须插入：

```text
problem_audit
→ model_design
→ data_preprocessing
→ solve_validate
→ result_analysis
```

模型设计阶段先锁定数据语义、允许处理和禁止处理；随后项目级预处理只执行一次。默认目录固定为：

```text
数据预处理/
├─ 数据预处理.py
└─ 数据预处理结果.xlsx
```

`数据预处理.py` 是共享原始数据的唯一直接读取者。它负责原始字段、维度、单位、坐标、缺失、异常、重复和题目专属数据质量审计，并执行已锁定的统一清洗、滤波、重采样、编码或坐标处理；不得求解任何小问核心模型，也不得为了某一问结果更好而反向调整统一预处理参数。

“一个总表”指一个统一 Excel 工作簿，而不是强行把不同物理对象拼成一个工作表。`数据预处理结果.xlsx` 至少包含 `运行配置`、`数据审计`、`预处理参数`、`预处理质量门`，并按题目对象设置中文数据工作表。该工作簿通过质量门后，所有 `问题X求解.py`、`问题X结果深化分析.py` 和数据型 MATLAB 流程只允许读取统一工作簿以及已验收标准结果工作簿，**禁止再次直接读取共享原始 CSV/XLSX/TXT 等附件**。

小问可以从统一工作簿构造题目专属派生特征，但不得重复执行项目级去缺失、异常处理、单位换算、统一滤波、统一重采样或坐标修正。若后续发现统一预处理口径必须改变，应回退本阶段，并将所有依赖小问结果、深化分析、图表和论文结果摘要标记 stale 后重新验收。

完整字段、质量门与 stale 传播规则以 `core/global_preprocessing_contract.yaml` 为唯一事实源。

## 4. 每问唯一数值交付目录

新项目每个小问只建立一个 `问题X求解/`。完成主求解、深化分析与 MATLAB 交接后，该目录默认恰好包含：

```text
问题X求解/
├─ 问题X求解.py
├─ 问题X求解结果.xlsx
├─ 问题X结果深化分析.py
├─ 问题X结果深化分析.xlsx
└─ qX_plot.m
```

两个 Python 文件职责分离。`问题X求解.py` 只负责主求解；主工作簿 accepted 后冻结。随后单独生成 `问题X结果深化分析.py`，读取已验收主工作簿、统一预处理工作簿和必要的已验收前问工作簿，完成题目专属深化分析。不得为了深化分析覆盖改写主求解脚本，也不得在该目录增加独立配置、运行说明、校验报告、图表目录或元数据文件。

若项目启用了全局统一数据预处理，本问两个 Python 文件不得直接读取共享原始数据源；出现该行为视为数据口径硬违规，而不是普通代码风格 warning。

## 5. 用户执行与质量门

项目级 `数据预处理.py` 与两个正式小问 Python 脚本均由助手生成并静态检查、由用户本地 full-fidelity 执行。统一预处理工作簿通过 `预处理质量门` 前，不得进入正式小问主求解。

两个正式小问 Python 脚本在各自交付前先通过语义治理门，再通过 `scripts/validate_code_delivery.py` 的静态执行配置与代码工程质量门；这些门不替代主结果和深化结果的数值质量门。

新项目默认采用 `execution_owner=user`、`execution_profile=full_fidelity`。助手负责审题、模型设计、公式闭环、统一预处理代码、完整版求解代码生成、静态检查和返回工作簿验收；用户负责实际运行题目专属代码。

助手不得运行、导入或间接执行题目专属统一预处理、主求解或深化分析脚本，不得自动缩减数据、网格、时域、场景、重复次数、迭代次数或放宽容差，也不得静默切换求解器或轻量近似。

完整运行配置分别嵌入对应阶段 Python，并写入对应工作簿的 `运行配置` 工作表。运行步骤和校验结果只在聊天或标准输出中返回，不额外落盘。主工作簿通过当前语义检查、运行配置、主脚本/统一数据哈希和 `主结果质量门` 后才能进入 `solved`；深化工作簿通过当前语义检查、深化脚本/统一数据哈希、`分析设计`、实质分析表和 `结论稳定性汇总` 后才能进入 `analyzed`。

## 6. 软件职责

- Python 统一预处理：只读取共享原始数据，完成项目级数据质量审计和统一预处理，输出唯一 `数据预处理结果.xlsx`；
- Python 主求解：读取统一预处理工作簿，完成模型求解、质量门和主工作簿；
- Python 深化分析：读取统一预处理工作簿、已验收主结果与必要前问结果，完成敏感性、鲁棒性、多算法、阈值、结构、场景或题型专项分析并输出深化工作簿；
- MATLAB：同目录 `qX_plot.m` 只读统一预处理工作簿和本问两个标准工作簿中的真实结果数据，精确匹配真实表头，不重新求解；
- LaTeX：默认论文主链；
- DOCX：仅在用户明确要求时加载，不是 LaTeX 前置。

MATLAB 默认只保留图窗，不创建 `图表/`，不自动导出 PNG、PDF 或 SVG。进入论文阶段后，用户人工确认并按需导出的正式图片放在项目级 `figures/`，不混入 `问题X求解/`。

## 7. 元数据与兼容边界

`run_info.json`、`result_manifest.yaml` 和 `matlab_figure_handoff.json` 只在用户明确要求完整复现包时生成，并放入项目级内部元数据目录，不得放入 `问题X求解/` 或 `数据预处理/`。

v7.1.x 及更早项目缺少统一预处理阶段时保持只读兼容；若重新进入模型设计或求解阶段，且存在跨问共享数据，应迁移到当前统一预处理结构。v7.0.x 项目缺少语义治理字段时，重新进入审题或模型设计阶段补齐当前 Problem Contract、语义闭环、复杂度复审和 semantic revision。v6.6.x 的单脚本四文件项目、旧 `结果数据表/问题X/` 和旧工作簿名继续只读兼容。新项目或重新进入深化分析阶段时使用当前五文件结构。

## 8. 正式交付同步

- 语义治理：`scripts/validate_semantic_governance.py`；
- 项目级数据预处理：`modules/03_data_preprocessing.md` + `core/global_preprocessing_contract.yaml`；
- 代码交付：`scripts/validate_code_delivery.py`；
- 用户返回工作簿：`scripts/validate_user_execution.py`；
- 图表、论文和提交包：`scripts/sync_project.py`。

语义治理门检查当前模型语义并传播跨问 stale；同步器继续只检查产物、哈希和下游 stale，不生成模型语义、数值结果或 passed 状态。统一预处理源数据、脚本、参数或结果工作簿变化使所有依赖小问及其下游失效；主脚本变化使本问主结果及全部下游失效；深化脚本变化只使本问深化结果及其下游失效。缺失用户返回的统一预处理或小问结果时必须暂停，不得生成示意数值。
