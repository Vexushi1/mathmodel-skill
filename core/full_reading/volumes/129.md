# Agent instructions

## Runtime tasks

1. Read `core/bootstrap.yaml` first at the project's fixed commit. Use `core/bootstrap.yaml#startup_contract` to select the opening scope before resolving the business action. The shared web/App entry is [PROJECT_INSTRUCTIONS.md#web-app-start](PROJECT_INSTRUCTIONS.md#web-app-start). For a new project, select v11_full_read as specified by that entry when the pinned source declares it. Keep an existing project's pin and startup choice. For an active selection, pass the applicable event and pinned commit to the resolver using --candidate-startup-event and --source-commit.
2. Follow that profile's source-reading instructions. When execution tools, the complete same-version resource root, dependencies and necessary project materials are available, run `scripts/resolve_runtime.py` with the current project root and intents for the stage, checks and waiting point. For new solve work without a project selection or explicit backend, pass `--solver-backend auto` to request a candidate. With GitHub-only access, take the original text from the fixed commit under the startup contract. Use `core/stage_reading_guide.md` and `core/runtime_assurance_contract.yaml#reading_plan.consumer_protocol` for subsequent stage reads. Report which text or checks remain unavailable. `scripts/resolve_workflow.py` is legacy stateless compatibility only.
3. Classify each subproblem with one objective, up to three structures and independent capabilities using `core/task_taxonomy.yaml`.
4. During Module 02, distinguish `proposed_model_spec` from `locked_model_spec`: after semantic closure and complexity sanity, run the two independent Model Challenge passes required by `core/model_approval_contract.yaml`, present the Model Approval Brief, and stop at `awaiting_model_approval` until the user explicitly approves the current semantic_revision and validated semantic_identity_hash. Silence or vague continuation is not approval, and a blocking challenge item cannot be waived by user approval.
5. Create or update project-root `模型论文框架.md` once the proposed model exists; keep only current semantics. Treat it as assistant-readable project memory, not merely a user-facing deliverable: when it exists and is current, read the relevant current-scope/subproblem/dependency/result/figure sections before downstream work instead of reconstructing the model from chat memory; read the full framework for cross-chat recovery, full-paper writing and final review. The framework includes Formula Trace, Algorithm Trace, current Model Challenge/Human Approval status, current writing-governance registries/claims and evidence locations; concrete numerical claims still require accepted-workbook verification, while project state owns revision/structured-identity/text-provenance/approval/stale status.
6. Before task-specific preprocessing or primary solve code is delivered, require both `scripts/validate_semantic_governance.py` and `scripts/validate_model_approval.py` to pass for the current questions. A semantic revision or structured identity change invalidates the previous challenge, approval and locked model until re-reviewed and explicitly re-approved; legacy semantic_hash approval is read-only provenance only.
7. Before any formal delivery, execute every gate returned in the resolver's current `pre_delivery_gates` sequence, in resolver order; do not maintain a second fixed gate list. When returned, `semantic_governance` validates current model semantics, `project_sync` runs with the resolved delivery scope and may write `sync_report.yaml`, and `submission_package_validation` performs the final package/manifest/hash check.
8. Semantic governance may read and audit legacy text-hash provenance for old projects, but legacy semantic hashes never authorize new project-level preprocessing or primary solve code and never restore numerical validity. The synchronizer never invents model semantics, results or passed validation; it only discovers artifacts, reads workbook structure, hashes files and propagates stale.
9. Under `core/user_execution_contract.yaml`, choose one Python/MATLAB numerical backend at the project root after reviewing foreseeable needs across all questions and before current numerical code delivery; every primary and activated analysis entrypoint inherits it. The choice and reason belong to `execution`, while `RUN_CONFIG` / `RUN_RECEIPT` record actual execution facts. A missing root choice or read-only `inspect` preview cannot authorize delivery. `scripts/project_solver_backend.py select` records the first explicit choice for a project with no numerical-stage history; even a `ready_for_review` preview cannot turn that case into `migrate`. Historical numerical projects or a change of the locked backend require an `inspect --migration-target` whole-project preview, confirmation bound to that project's state bytes, generation, target and effects, then an explicit `migrate --confirm-migration`. Authorization to implement repository code does not authorize migration of any particular user project. Project-level preprocessing remains Python. After primary acceptance, execute the Analysis Necessity Gate: only `required` activates the independent result-analysis code and analysis workbook; `not_required` requires a non-empty reason and creates neither 03B artifact. Formal MATLAB figure code reads exact unique headers from the current legal workbook set in the same question directory and draws formal figures. LaTeX is the default paper and final-PDF path; DOCX is an explicit optional review branch and is not a LaTeX prerequisite.
10. New projects always use `问题X求解结果.xlsx`; `问题X结果深化分析.xlsx` exists only when the Analysis Necessity Gate is `required` and 03B execution is accepted. Historical naming is handled only by dedicated compatibility contracts and must not be generated by active templates. A `not_required` disposition does not imply that robustness, stability or alternative-method consistency has been tested.
11. Task-specific solve/result-analysis code is user-executed at full fidelity under `core/user_execution_contract.yaml`; do not run it in the assistant or silently reduce data, grid, horizon, repetitions, tolerance or solver fidelity.
12. After startup, apply `packs/artifact/proposition_proof.md` only for explicit proof requests or a nonzero proposition plan. Apply `packs/artifact/algorithm_flow.md` for an explicit paper-algorithm request or a writing/review route that must consume a current `stepwise/pseudocode` Algorithm Trace. The complete-deliverable `full_workflow` route may also keep this small Pack in context across its user-execution boundary so later paper stages do not lose the presentation contract; ordinary `full_solution` / `code_and_solution` omit it from their stage plan. Plain “算法/求解” remains a numerical-solution intent; do not route it to pseudocode presentation. Do not load `legacy/` by default.
13. When an Algorithm Trace is used, preserve the chain `model/formula/proposition/constraint → paper algorithm → real code implementation → accepted workbook result/evidence`; machines may check declared fields and anchors but must not infer algorithm correctness or convergence from step text.

14. For a new project, register every audited Qn and typed dependency in the first approved-to-propose project specification; after the first real `proposed_model_spec`, `scripts/initialize_project.py` may atomically create the State/framework without inventing approval. On an existing project, `resolve_runtime.py` selects at most one question per operation and only as a read-only plan; `sync_project.py --question Qn` is a separate optional question-level artifact view for design/code/results/figures, not Model Approval or Code Delivery. Never narrow shared project preprocessing or final docx/latex/submission gates; full graph stale propagation remains the existing State Transition Authority.

## Phase E — Artifact Naming Migration

**建议版本：** `8.9.0` minor（additive）；最终删除旧字段留给 9.0.0。

### 修改

Schema 新增：

```yaml
artifact_hashes:
  primary_code:
  analysis_code:
```

并逐步停止新项目写：

```yaml
artifact_hashes.model
```

### 迁移规则

```text
legacy artifact_hashes.model -> primary_code
```

只有在没有新字段时读取 alias；若新旧同时存在且值不同：

```text
blocking inconsistency
```

### `model_hash` 处理

实施前执行全仓库引用盘点，形成记录：

```text
field -> readers -> writers -> semantic meaning -> migration action
```

没有引用证据前不删除。

### 验收

- 新项目状态输出没有含混 `model` artifact；
- old project 仍能读取；
- primary code change 不会自动等价为 mathematical semantic change；
- code delivery、sync、runtime assurance 命名一致。

## Phase F — Transactional Project Writes

**建议版本：** `8.9.x` minor。

### 修改

- 新增 `project.state_generation`；
- 新增 `scripts/project_transaction.py`；
- `sync_project --write` 全部走 staged + validated + recoverable commit；
- semantic governance `--write` 也不得继续直接裸写 state；
- 其他活动脚本若会更新同一 state，逐一纳入共享 transaction helper。

### 测试

- atomic single-file replace；
- simulated crash recovery；
- generation conflict；
- concurrent stale writer rejection；
- transaction journal cleanup；
- repeated sync idempotence；
- failed validation 不留下半写 framework/state。

### 明确不做

不引入数据库，不引入外部锁服务；保持仓库文件型工作流。
