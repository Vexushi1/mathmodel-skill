## 运行时入口

资源路径相对于包含 `core/bootstrap.yaml` 和 `.codex-plugin/plugin.json` 的仓库/插件根目录。根 `SKILL.md` 使用自身目录；`skills/mathmodel-skill/SKILL.md` 使用自身目录上两级。

1. 读取 `core/bootstrap.yaml`，沿用项目固定 commit；
2. 按 `core/workflow_router.yaml` 的 `default_load` 读取 `core/hsk_core_policy.md`。新项目采用 `PROJECT_INSTRUCTIONS.md#web-app-start`，在固定提交支持时启用 `v11_full_read`。已有项目沿用原选择，按 `core/bootstrap.yaml#startup_contract` 选择正式、局部或恢复范围；
3. 从同一提交读齐所选规则正文，补齐缺段，再开始当前动作。正式开场及阶段读取分别服从 `core/runtime_assurance_contract.yaml#reading_plan.formal_rule_delivery` 和 `reading_plan.consumer_protocol`；
4. 读取当前 `模型论文框架.md` 恢复模型、双审、批准和证据位置。模型批准按 `core/model_approval_contract.yaml`，结果接续按 `core/user_execution_contract.yaml#result_handoff`，数值质量按 `core/numerical_verification_contract.yaml`；
5. 需要机器诊断时显式调用 `scripts/resolve_runtime.py`，提供项目根与当前小问。调用其启动选择时同时传入 `--candidate-startup-event` 和 `--source-commit`。机器读取可用 `scripts/read_stage.py`，GitHub 正文导航见 `core/stage_reading_guide.md`；
6. 普通写作按 Template Manifest、Paper Writing Protocol 和 compact writing runtime 渐进读取，按最终 active assembly 执行 Cross-File Chapter Handoff。复杂数学与证据读取 `core/writing_reasoning_contract.yaml`，终审读取 `modules/06_review_delivery.md`；
7. `legacy/` 不进入默认执行链，旧 `scripts/resolve_workflow.py` 保留无状态兼容入口。

## 默认执行

按全题已知需求和当前模型选择项目统一的 Python/MATLAB 数值后端，将选择与理由登记到项目根 `execution.solver_backend`。用户运行对应的完整求解代码，返回工作簿后按 `core/user_execution_contract.yaml#result_handoff` 核对结果并接续。

显式调用 `scripts/resolve_runtime.py` 时，指定后端使用 `--solver-backend python` 或 `--solver-backend matlab`；新项目未选时使用 `--solver-backend auto`。`scripts/project_solver_backend.py select` 登记首次选择；历史项目或后端变更使用 `inspect --migration-target` 查看全题影响，确认后执行 `migrate --confirm-migration`。具体项目后端与迁移行为由 `core/user_execution_contract.yaml` 定义。

### 项目工作记忆

从 `模型论文框架.md` 恢复当前模型、人工批准及证据位置，读取实际工作簿中的数值。`state/project_state.yaml` 保存项目登记与实际机器状态。

### 项目级登记与逐问推进

新项目登记全题 Problem Contract 与已确认的 typed `depends_on`。第一份真实 `proposed_model_spec` 形成后建立 State 与框架，可使用 `scripts/initialize_project.py`。已有项目按当前请求和框架继续选定的小问。

显式调用 `scripts/resolve_runtime.py` 时传 `--question Qn`；`scripts/sync_project.py --question Qn` 支持单问 `design/code/results/figures` 产物检查。默认项目同步及正式 `docx/latex/submission` 工具保持全项目范围和完整依赖传播。

## 主链

`通用数据审计` → `条件数学化与结构化简` → `最小充分主模型 + 按需 comparator` → `preprocessing_decision` → `proposed_model_spec` → `Model Reviewer + Devil's Advocate` → `awaiting_model_approval` → explicit Human Model Approval → `locked_model_spec` → resolver-selected preprocessing / solve / analysis stages。

## 目录、正式交付

目录与交付文件服从 `core/output_contract.yaml`。LaTeX 工具入口是 `scripts/audit_latex_project.py`；显式机器验收通过后记录 `validated_submission_package`。

## 稳定硬边界

- 形成 `proposed_model_spec` 后完成独立 Model Reviewer、Devil's Advocate 和明确人工批准，保存当前模型与批准依据，再进入项目级预处理或主求解代码交付。
- 题目专属预处理、Python/MATLAB主求解与结果深化代码由用户本地按 `full_fidelity` 执行；助手负责生成、静态检查和验收返回 artifact，不得静默降采样、放宽容差、缩短时域或切换求解器。
- 模型与批准从当前框架恢复，数值从真实工作簿读取；机器字段按实际工具执行结果维护。
- 主求解数值质量服从 `core/numerical_verification_contract.yaml`；实际结果核对后，由结果分析模块处理必要的替代场景、敏感性及稳健性分析。
- MATLAB 绘图入口只消费已验收求解实现的数据/工作簿进行 Figure Evidence，不重新预处理或求解；正式图名由 LaTeX/DOCX caption 承担。
- 可编辑 draw.io 只服务后端选择门确认的非数据驱动题目专属机理图；确定性结构检查不替代渲染预览、箭头语义或数学正确性人工复核。
- LaTeX 是默认论文主链；CUMCM 结构先由 Template Manifest 确定，再逐章读取当前写作规则。DOCX 只在用户明确要求 Word 载体时加载。
- 显式启用机器验收时，按 resolver 当前返回的 `pre_delivery_gates` 顺序执行。
- 仓库修改遵守 `SKILL_CHANGE_GOVERNANCE.md`。Branch Protection 若因平台权限不可用，只记录为平台治理债务，不得用 Skill 代码伪造。

求解语言参数按上文“默认执行”传入；后端决策与旧调用兼容只服从 `core/user_execution_contract.yaml` 和 runtime assurance，不把 MATLAB 一词自动路由为绘图。
