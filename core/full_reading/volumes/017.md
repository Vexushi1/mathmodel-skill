model_challenge:
  principle: independent_two_pass_review
  reviewer_pass:
    role: positive_fitness_review
    must_check:
    - problem_contract_fit
    - required_answer_closure
    - route_selection_fit
    - variable_and_constraint_closure
    - objective_alignment
    - formula_trace_closure
    - preprocessing_fit
    - structure_before_algorithm
    - literature_method_transfer_when_used
    - literature_source_qualification_when_used
    - full_fidelity_computability
    - selected_backend_capabilities_and_environment
    - validation_plan_adequacy
    - paper_explainability
  devils_advocate_pass:
    role: adversarial_model_challenge
    must_check:
    - alternative_problem_interpretation
    - output_omission_or_substitution
    - forbidden_or_convenience_assumptions
    - unused_problem_conditions_or_attachment_fields
    - semantic_damage_from_preprocessing
    - hidden_coupling_or_invalid_decoupling
    - dynamic_to_static_or_multi_agent_collapse
    - inactive_key_constraints
    - local_property_misstated_as_global
    - simpler_baseline_may_be_sufficient
    - problem_may_have_been_implausibly_over_simplified
    - literature_recency_anchor_and_novelty_bias_when_used
  check_semantics:
    required_answer_closure: >-
      Trace every Qn-REQ-xx answer back to input data, mathematical relations and
      algorithm return values. Check object, granularity, units and tie/event rules;
      record the expected output location in the existing semantic-closure table.
    output_omission_or_substitution: >-
      Independently enumerate required answers from the original prompt. Challenge
      omissions, aggregate answers substituted for per-object answers, missing peak
      times and incompatible granularity, without adopting the first pass's checklist.
    route_selection_fit: >-
      Compatibility check id. Interpret it as whether the current selected model is the
      minimal-sufficient main model after Condition -> Consequence and justified reduction,
      not as a requirement to choose between a fixed classic Route A and advanced Route B.
    structure_before_algorithm: >-
      Require problem conditions, definitions, invariants and task-specific structure to be
      converted into mathematical consequences before solver selection. Exact/proven-sufficient
      reduction should be used before escalating generic algorithm complexity.
    simpler_baseline_may_be_sufficient: >-
      Adversarial minimal-sufficiency check: if a simpler model can still answer the full prompt
      with required mechanisms, constraints, precision and outputs, the current main model needs
      repair or explicit justification. A simple baseline may also remain only as a comparator.
    literature_method_transfer_when_used: >-
      If the current proposed model consumes outside research, independently verify
      the original paper's object, assumptions, variables, constraints, data needs
      and the current problem's transfer conditions. Presence of a citation or a
      structurally valid literature JSON report does not prove applicability.
      Without externally dependent model relations, this check is not_applicable.
    literature_source_qualification_when_used: >-
      For critical outside methods, empirical parameters and nontrivial theories,
      retain actual source access and original-method anchors or explicit unresolved
      evidence. E0/E1 summaries cannot establish a verified formula; where a
      critical external premise remains unsupported, require repair before PASS.
    literature_recency_anchor_and_novelty_bias_when_used: >-
      Independently challenge recentness bias, inaccessible original methods,
      incompatible boundary/data regimes, omitted counterexamples and unsupported
      claims of first invention; do not demand a fixed number of citations.
  independence_rule: >-
    The reviewer and devil's-advocate passes must form conclusions independently.
    When native parallel agents are available they may run in parallel; otherwise run
    two separate review passes and do not use the first verdict as the starting point
    of the second.
  severity_policy:
    blocking: repair_in_model_design_before_approval
    review_required: repair_or_record_specific_justification_before_pass
    warning: may_remain_but_must_be_exposed_in_approval_brief
  pass_rule: >-
    model_challenge_status may become passed only when no blocking item remains and
    every review_required item has been repaired or explicitly justified.
  no_user_override_of_blocker: true
