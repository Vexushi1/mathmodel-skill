# Module 01：题目审计、任务拆解与题意口径冻结

## 目标

从题干和附件建立不遗漏、可执行的需求地图，并在进入模型设计前形成可审查的 `problem_contract`。本模块的核心任务不是选模型，而是确认“题目到底要求研究什么、允许改变什么、哪些关系能够从题面推出”。

## 执行步骤

1. 识别竞赛、题号、附件、数据格式、显式交付物和数值精度；
2. 逐句拆分背景、对象、已知条件、规则、显式约束、隐含约束和评价重点；
3. 每问说明直接目标、隐含目标、数据、依赖、设问意图、最终交付、机制解释需求和评委风险；
4. 按 `templates/problem/requirement_coverage.md` 建立“题目要求—模型/代码—结果表/图—论文位置—附录”覆盖表；同一问的各项必答量分别编号为 `Q1-REQ-01`、`Q1-REQ-02`，逐项记录原文、对象/粒度、单位与所需最终答案；
5. 只有改变模型、数据口径、约束或结论的歧义才向用户确认；
6. 按 `core/task_taxonomy.yaml` 为每问确定一个 objective、至多三个 structures 和独立 capabilities；
7. 为兼容旧 Pack，输出由 objective/structures **完整派生且去重**的 `legacy_task_packs`，不得人为截断，也不得将其作为唯一分类事实；
8. 输出字段—含义—单位—粒度—关联键的初步 data schema；
9. 标记待证明关系，命题准入在 Module 02 按需处理；
10. 为每问建立 `problem_contract`，完成题意口径冻结。
11. 仅在冻结之后，将尚待外部核实的领域机制、非显然方法来源和参数需求标成后续 Research Brief 的候选疑问；审题阶段不因这些疑问提前检索、选主模型或申请锁模。

## Problem Contract：题意口径冻结

每问必须明确以下内容，先形成本阶段可审查的 `problem_contract`；正式 `模型论文框架.md` 按现有 `output_contract.model_paper_framework.create_after=proposed_model_spec` 创建后，再将题意口径同步至对应小问“当前模型口径”。不得为检索或跨聊天恢复擅自提前创建正式框架：

| 字段 | 要求 |
|---|---|
| 研究对象 | 题目真正要求研究、预测、评价或优化的对象 |
| 原始对象 | 题面和附件直接定义的对象，不得被计算便利性替换 |
| 派生对象 | 由题面对象通过明确数学关系构造的对象，并写出来源 |
| 已知量 | 题面或附件直接给出的量 |
| 可计算量 | 可由已知量严格推出的量，注明推导关系 |
| 决策变量 | 题目允许主动改变的量 |
| 状态变量 | 系统演化、仿真或约束中变化但非直接决策的量 |
| 输出量 | 按需求编号逐项列出题目要求报告、比较或提交的量，注明对象/粒度、单位、精度与并列值或未触发事件的处理 |
| 显式约束 | 题面直接规定的边界、规则和限制 |
| 隐含约束 | 必须由几何、物理、统计、逻辑或业务机制推出，并给依据 |
| 禁止假设 | 题目不能支持、但容易因为数据结构或计算方便而误加的条件 |
| 数据角色 | 每个附件或字段属于输入、标定、验证、边界还是结果观测 |
| 小问依赖 | 依赖前问的数据、参数、模型或结果，标明 dependency kind |

冻结原则：

- 不得根据附件呈现形式、已有代码结构、求解方便性或“结果看起来合理”反推题意；
- 不得将“数据中可以重构出的对象”自动替代“题面原始对象”；
- 隐含约束必须能够追溯到题面、附件说明或明确机制；
- 若关键歧义会改变对象、变量、约束或最终结论，`problem_contract_status` 保持 `pending`，不得进入 Module 02；
- 完成后将小问 `problem_contract_status` 置为 `frozen`。后续题意解释、数据角色或小问依赖发生变化时，立即改为 `stale` 并重新审题。

## 审题后的文献研究需求交接（不执行搜索）

- 仅当当前小问 `problem_contract_status=frozen`，才可把题面所需但不能直接从题面、附件、定义或严格推导获得的领域事实、本构机制、外部参数或方法适用条件，标为 Module 02 的检索疑问候选。
- 候选疑问至少保留小问编号、真实研究对象、对应题设条件/约束、未知的数学机制、可用数据、禁止引入的便利假设和期望外部证据用途；不要在本模块依据文献标题选择模型。
- 这些信息属于既有 requirement map / risks 的组成部分，不新增机器 Artifact、Project State 字段、独立文献 Gate 或固定文献篇数。单纯审题请求仍停在审题交付点。
- 实际的 Research Brief、网络检索、来源核验、方法迁移和自主模型构造，只在 Module 02 的新设计/实质修订范围内启动，遵守 `core/literature_research_contract.yaml`；无外部证据需求的自洽纯数学任务可以合理记录不需要检索。
- 在 `proposed_model_spec` 创建正式框架之前，不能把聊天输出或临时研究记录宣称为已验证的持久项目文件；跨聊天无法核实时必须重新核对题目和实际来源。

## 小问依赖 DAG

依赖必须区分类型，而不是只写“Q2依赖Q1”：

- `data`：继承前问整理或生成的数据；
- `parameter`：继承前问估计、标定或优化得到的参数；
- `model`：继承前问模型结构、状态方程、几何关系或约束体系；
- `result`：直接使用前问的数值结果、方案或排序。

项目状态中的 `depends_on` 使用 `question + kind + note` 记录。语义修改时，依赖关系用于跨小问 stale 传播。

## 最低输出

- requirement map 与 subproblem map；
- 小问依赖 DAG；
- 每问 `problem_contract` 与 `problem_contract_status=frozen`；
- 每问 classification、置信度、capability 与兼容 Pack；
- data schema、附件清单和关键风险；
- 下一阶段所需输入，包括归属于既有 requirement map / risks 的研究疑问候选（若有）；它们不是已执行检索或已确认模型的证据。

## 阶段门槛

进入 Module 02 前，当前待设计小问必须满足：

1. `problem_contract` 字段完整；
2. 原始对象、派生对象、决策变量、状态变量和输出量没有混淆；
3. 显式约束与隐含约束来源可追溯；
4. 附件和字段的数据角色明确；
5. 小问依赖类型明确；
6. `problem_contract_status=frozen`。

不满足时继续审题，不得通过先写代码、先拟合数据或先看结果来替代口径冻结。

## 禁止事项

不在本模块给大段代码；不把题干摘抄当问题分析；不按项目级标签覆盖所有小问；不承诺数据无法支持的因果结论；不允许以“计算更简单”作为改变题意对象或约束的依据。

# Module 02：模型设计、语义闭环、复杂度复审、独立挑战、人工锁模与论文框架

本模块负责把审题结果转成可求解、可验证、可写作的当前模型语义。跨竞赛的公式推理、Model/Solver/Validator 角色、优化模型表达、**Model Construction Rationale**、Algorithm Trace、规则等级、命题预算和 Citation Evidence 由 `core/writing_reasoning_contract.yaml` 唯一定义；Model Challenge 与 Human Model Approval 的唯一行为合同为 `core/model_approval_contract.yaml`；主求解内在数值有效性的字段级规则由 `core/numerical_verification_contract.yaml` 唯一定义。本模块只记录本题实际选择，不复制第二套写作、审批或数值验证规范。

## 0. 前置条件

题意和结构明确后，可按需选择 `case_memory_retrieve`，依照 `packs/artifact/case_memory_retrieval.md` 比较既有模式、条件差异与不可迁移项，并显式记录采用/拒绝理由及本题证据。它提供有边界的建议；当前模型的语义闭环、Model Challenge 与 Human Model Approval 仍按原 Authority 执行。

只接受 `problem_contract_status=frozen` 的小问。若题意对象、数据角色、约束来源或小问依赖仍存在会改变答案的歧义，退回 Module 01；不得通过代码试错替代审题。

Problem Contract 冻结只回答“题目是什么意思”，不等于模型已获准进入代码阶段。正式任务代码前还必须依次完成当前模型语义闭环、Complexity Sanity、独立 Model Challenge 和用户 Human Model Approval。

## 1. 初始化结构发现、条件驱动化简与主模型生成

本阶段**禁止以“先选模型名、再把题目塞进去”作为默认建模方式**。在提出标准模型类型、正式模型名称或 solver 之前，先回答“题目条件已经替我们解决了多少问题”，把冻结后的 Problem Contract 转成当前小问的数学本体。

### 1.1 问题本体初始化

先区分并登记真正会改变模型的对象：

```text
研究对象 / 索引集合
→ 状态变量 / 决策变量 / 外生输入 / 观测量 / 输出量
→ 定义关系 / 硬条件 / 守恒或不变量
→ 本构或经验关系 / 时空或图结构 / 信息结构 / 随机结构
→ 变量基准、单位、参考系
→ 初始 / 边界 / 终止 / 可行条件
```

特别区分以下语义，不得把它们全部包装成“模型假设”：

- `definition`：定义恒等式、比率或记号关系；
- `hard_condition`：题面明确给出的硬条件；
- `invariant`：守恒量、总量、不变量或恒等约束；
- `constitutive`：本构、经验、响应或拟合关系；
- `observation`：附件/数据直接支持的事实；
- `assumption`：题面未给出、为闭合模型而新增的真实假设；
- `approximation`：数学、物理或统计近似；
- `decision`：可控变量、动作或策略。

若两个同名量采用不同基准、参考系、时间口径或统计口径，应先拆分定义再建模，禁止依赖后文文字补救。

### 1.2 Condition → Consequence：题目条件先转成数学后果

逐条处理会影响模型的题设条件，不停留在“记录条件”，而应尽量形成：

```text
题面条件 / 定义 / 数据事实
→ 数学性质或关系
→ 对变量、状态空间、可行域、计算域或信息集的影响
→ 是否能消元、降维、分解、排序、聚合、缩域或等价变换
```

题目条件优先被视为**潜在的降复杂度信息**，而不只是需要追加给 solver 的约束。典型可利用结构包括但不限于：

- 定义与恒等关系、守恒与不变量；
- 几何/周期/交换对称与等价类；
- 单调性、支配关系、阈值或边界最优；
- 凸性、凹性、拟凸性；
- 可分离性、少量耦合约束、分层/递推结构；
- 排序与 exchange argument；
- 稀疏性、局部性、带状/块带状结构；
- tree / DAG / bipartite / flow / matching 等拓扑；
- 时间/空间尺度、小参数、无量纲关系；
- 最小充分状态、充分统计量；
- 独立性、条件独立、期望线性、确定性等价等概率结构；
- 对数、比值、累计量、势函数、坐标映射、特征分解等等价变量变换；
- “首次、各处、低于、不超过、持续满足”等 predicate / event 结构；
- 决策时点可知信息、先后决策与时间因果。

是否成立必须由题面、数据、定义或数学推导支持，不能仅凭题型标签机械宣告。

### 1.2A 文献证据增强型模型研究（新设计/实质修订时）

本节在前述 **Problem Contract 冻结与独立题目结构判断**之后、正式最小充分主模型确定之前执行。检索与方法证据的唯一细则在 `core/literature_research_contract.yaml`，执行说明见 `packs/artifact/literature_research.md`。当前任务只需记录本题实际使用的方法依据、未解决条件和选择理由；不复制第二套 Citation Evidence 或审批规则。
