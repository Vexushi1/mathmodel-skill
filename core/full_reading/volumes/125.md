# Agent instructions

## Runtime tasks

1. Read `core/bootstrap.yaml` first at the project's fixed commit. Follow `core/bootstrap.yaml#startup_contract` and [PROJECT_INSTRUCTIONS.md#web-app-start](PROJECT_INSTRUCTIONS.md#web-app-start). For a new project, select v11_full_read when the pinned source declares it. Keep an existing project's pin and startup choice. When invoking the resolver for this selection, pass --candidate-startup-event and --source-commit together.
2. Read the selected rule text directly from that commit and supplement missing ranges. Begin problem analysis after the formal full read. Use `core/stage_reading_guide.md` and `core/runtime_assurance_contract.yaml#reading_plan.consumer_protocol` for subsequent stage reads.
3. Classify each subproblem with one objective, up to three structures and independent capabilities using `core/task_taxonomy.yaml`.
4. During Module 02, follow `core/model_approval_contract.yaml`: form `proposed_model_spec`, complete the independent Model Reviewer and Devil's Advocate passes, present the Model Approval Brief, and wait at `awaiting_model_approval` for explicit user approval. Save the approved model and the user's approval evidence in the framework.
5. Create or update project-root `模型论文框架.md` once the proposed model exists. Read its relevant model, approval, dependency, result and figure sections before downstream work; read the complete current framework for cross-chat recovery, full-paper writing and final review.
6. Resume the approved current model from the framework and read the actual inputs needed by the selected question. Apply `core/model_approval_contract.yaml` to real model changes and `core/user_execution_contract.yaml#result_handoff` to returned results. Record machine fields only from actual tool runs.
7. For explicitly requested machine validation, execute every gate returned in the resolver's current `pre_delivery_gates` sequence, in resolver order. Use `scripts/resolve_runtime.py` with the project root and `--question Qn`; `scripts/resolve_workflow.py` remains the stateless compatibility entry.
8. Explicit semantic-governance tools retain legacy text-hash provenance; legacy semantic hashes never authorize new project-level preprocessing or primary solve code in that machine path. The synchronizer discovers artifacts, reads workbook structure and propagates stale.
9. Choose one Python/MATLAB numerical backend after reviewing foreseeable needs across all questions and the current model, following `core/user_execution_contract.yaml`. Register the choice and reason at the project root. Use `scripts/project_solver_backend.py select` for an explicit first selection; review the project's affected stages before a backend change. Project-level preprocessing remains Python. After checking primary results, evaluate Analysis Necessity Gate: `required` activates 03B, while `not_required` records a reason and continues to figures or writing.
10. New projects use `问题X求解结果.xlsx`; `问题X结果深化分析.xlsx` is produced when 03B is required. Figure code reads the actual workbooks needed by the selected figure. LaTeX is the default paper path; DOCX serves an explicit Word request.
11. Task-specific solve/result-analysis code is user-executed at full fidelity under `core/user_execution_contract.yaml`; preserve the data, grid, horizon, repetitions, tolerance and solver fidelity.
12. Apply `packs/artifact/proposition_proof.md` for explicit proof requests or a nonzero proposition plan. Apply `packs/artifact/algorithm_flow.md` for a paper-algorithm request or a writing/review route consuming a current `stepwise/pseudocode` Algorithm Trace. The complete `full_workflow` route keeps this Pack across user execution; ordinary `full_solution` / `code_and_solution` omit it from their stage plan. Numerical solving follows the numerical route. Keep `legacy/` outside default reads.
13. When an Algorithm Trace is used, preserve `model/formula/proposition/constraint → paper algorithm → code implementation → actual workbook evidence` and review its mathematical meaning.
14. Register all audited Qn and typed dependencies before selecting the current model. After the first real `proposed_model_spec`, `scripts/initialize_project.py` can create State and framework. On existing projects, select the question from the current request and framework; explicit resolver calls require `--question Qn`. Use `sync_project.py --question Qn` for question-level artifact inspection; project preprocessing and final `docx/latex/submission` tools retain project-wide scope.

## Phase E — Artifact Naming Migration

**建议版本：** `8.9.0` minor（additive）；最终删除旧字段留给 9.0.0。

### 修改

Schema 新增：

```yaml
artifact_hashes:
  primary_code:
  analysis_code:
```

并逐步停止新项目写：

```yaml
artifact_hashes.model
```

### 迁移规则

```text
legacy artifact_hashes.model -> primary_code
```

只有在没有新字段时读取 alias；若新旧同时存在且值不同：

```text
blocking inconsistency
```

### `model_hash` 处理

实施前执行全仓库引用盘点，形成记录：

```text
field -> readers -> writers -> semantic meaning -> migration action
```

没有引用证据前不删除。

### 验收

- 新项目状态输出没有含混 `model` artifact；
- old project 仍能读取；
- primary code change 不会自动等价为 mathematical semantic change；
- code delivery、sync、runtime assurance 命名一致。

## Phase F — Transactional Project Writes

**建议版本：** `8.9.x` minor。

### 修改

- 新增 `project.state_generation`；
- 新增 `scripts/project_transaction.py`；
- `sync_project --write` 全部走 staged + validated + recoverable commit；
- semantic governance `--write` 也不得继续直接裸写 state；
- 其他活动脚本若会更新同一 state，逐一纳入共享 transaction helper。

### 测试

- atomic single-file replace；
- simulated crash recovery；
- generation conflict；
- concurrent stale writer rejection；
- transaction journal cleanup；
- repeated sync idempotence；
- failed validation 不留下半写 framework/state。

### 明确不做

不引入数据库，不引入外部锁服务；保持仓库文件型工作流。

## v8.0.0 模板吸收原则

吸收：

- 一级章顺序；
- `模型准备` 的共享基础模型角色；
- 每问独立一级章；
- 问题内部 MODEL → SOLVE → RESULT → VALIDATE 的局部闭环；
- 结果与验证就地闭环；
- 末尾模型评价。

不机械复制：

- 固定五问数量；
- 具体二级/三级标题；
- 任何题目专属公式、算法、参数、图表和结论；
- 为了编号一致强制保留不适用章节。
