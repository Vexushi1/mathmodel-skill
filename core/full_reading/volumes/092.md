# 命题与证明按需 Pack

仅在用户明确要求命题/证明，或全文命题计划非零时加载。命题不是装饰理论，必须服务当前模型、计算、理论边界或关键结论。

命题数量按 `core/writing_reasoning_contract.yaml#proposition_governance` 执行：**全文正文正式命题最多 4 个，不设超额例外**。先合并可以共用证明的同质命题，非核心技术细节可放入附录；核心证明和关键推导必须保持正文数学闭环，不因压缩正式命题数量而删除。

## 一、准入

命题至少完成一项实际建模作用：

1. 证明原问题与变量替换、坐标变换、线性化或图论转换等价；
2. 证明可行解存在、唯一，或算法操作保持可行；
3. 证明单调性、阈值、凸性、边界最优性或候选集结构；
4. 严格缩减变量、搜索范围或冗余约束；
5. 给出稳定性、误差界、性能界或理论上下界；
6. 核验本题满足某标准定理条件并据此得到关键结论；
7. 给出直接改变后续求解或解释的解结构性质。

变量定义、直接代数变形、题意复述、单个样本结果、准确率比较和求解器退出状态不得包装成命题。

## 二、内部记录

每个命题记录：

- ID：`P1, P2, ...`，按当前计划连续或稳定编号；
- 对应小问；
- 命题类型；
- 前提、定义域与参数范围；
- 核心结论；
- 证明等级；
- 建模作用；
- 下游模型/计算作用；
- 数值复核；
- 失效边界；
- 状态：candidate/current/stale/removed。

旧项目若保留 `budget_exception_reason`，仅作历史说明，不构成正文超过 4 个命题的豁免；新正文超限时必须调整命题安排，而不能用理由字段直接放行。

## 三、下游作用

至少回答一种：

- 是否降维、删约束、缩小候选区域或搜索区间；
- 是否证明变换、分解或近似在当前条件下合法；
- 是否保证算法操作或候选解保持可行；
- 是否给出阈值、上下界、单调方向、停止条件或解结构；
- 若不直接改变计算，是否明确支撑某个模型必要性或正文结论。

如果说不清下游作用，优先改为普通推导而不是保留正式命题。

## 四、证明等级

- **A：完整证明**；
- **B：关键证明链**，正文常用；
- **C：引用标准定理并核验本题条件**。

3--8 行、2--6 个步骤等均为 Recommendation，只帮助组织阅读，不是数学有效性、正文位置或交付否决条件。证明位置由数学作用决定而不是由长度决定：凡承担模型成立、关键变换合法性、核心结论、关键边界/可行性/唯一性或下游计算前提的核心证明，正文必须完整可恢复；即使超过半页，也不能仅因长度移入附录。只有不影响主论证闭环的技术引理、重复展开或扩展证明可以放入附录，正文应明确引用与作用。

A/B/C 证明等级描述证明方式与证据来源，不代表“正文/附录”等级。数值复核只能辅助证明，不能代替证明。

## 五、证明组织：分段优先，分点按需

正文 B 级证明优先采用自然分段 + 必要公式。连续推理能顺着定义、公式和条件直接得到结论时，不为了“看起来清晰”机械拆成 1、2、3。

适合分点的典型情形：

- 分情况讨论；
- 先证存在再证唯一；
- 多个独立条件分别验证；
- 先构造映射，再验证可行域保持，最后验证目标保持；
- 多个引理或性质存在清晰先后阶段。

无论自然分段还是分点，每个逻辑单元只承担一个主要推理动作。必要公式单独呈现，避免一句话塞入多个关键推理。

证明结束后，框外另起正文段说明其**模型作用与计算落点**，具体指出后续哪个变量、约束、候选域、算法步骤或判断因此变化。

## 六、编号与排版

- 正文显示编号使用阿拉伯章节号，如“命题 4.1”“命题 6.2”；
- 内部 `P1, P2, ...` 只用于项目追踪，不直接替代论文编号；
- 命题正文与短证明可置于同一外框，框内不套第二层边框；
- 外框白底、细边、无阴影和大面积底色，可用黑、深灰或克制深蓝；
- 证明以黑体“证明：”起始，以空心方块结束；
- 排版不能决定证明去留。短证明可与命题陈述同框；核心证明较长时，命题陈述可保留在命题框，随后立即在正文用 `hskproof` 或自然证明段落完整展开并允许正常分页，不缩小字号、不删关键步骤，也不因整框无法同页而移附录；
- 只有不承担正文主论证闭环的补充证明/技术引理才可放附录，并在正文给出明确引用和作用；
- 流程图和机理图的彩色框限制不适用于命题证明环境；
- 命题与证明使用正文样式，不生成额外目录项。

## 七、LaTeX 形态

默认短证明：

```latex
\begin{hskproposition}{时间--深度映射的单调性}
\label{prop:monotone}
在条件……成立时，映射……严格单调。
\begin{hskproof}
由定义可写出
\begin{equation}
T(z)=\int_0^z f(\zeta)\,\mathrm d\zeta .
\end{equation}
在当前定义域内有 \(f(\zeta)>0\)，故 \(\mathrm dT/\mathrm dz>0\)。因此 \(T(z)\) 严格递增并存在唯一逆映射，命题得证。
\end{hskproof}
\end{hskproposition}
```

框后正文继续说明：唯一逆映射使后续变量怎样转换、搜索怎样缩小或判定怎样简化。

若核心证明较长，可把 `hskproposition` 只用于命题陈述，结束命题框后紧接 `hskproof` 在普通正文流中展开完整证明；现有 `hskproof` 不依赖必须嵌套于命题框。是否这样排版只由可读性和分页决定，不改变“核心证明留正文”的数学位置。

模型、参数、约束或定义域变化时，相关命题立即重新核验；旧证明若不再成立则标记 stale 并从 current 正文移除。

# 审查交付适配器

本 Pack 只适配 `modules/06_review_delivery.md` 及 `core/module_manifest.yaml#modules.review_delivery.reading_sources` 声明的终审来源，不复制检查规则。审查报告先按致命、重要、一般问题排序，再给六维评分；每个 finding 必须给出规则来源、验证方式、位置、证据、原因和可执行修复动作，不能只给总分。

审查前按 resolver 当前返回的 `pre_delivery_gates` 顺序执行适用检查。仅审阅或只读请求不写入项目；正式提交交付时再消费对应 scope 的同步与提交门，不能直接套用固定 `submission --write` 命令。

```bash
python scripts/validate_model_paper_framework.py 模型论文框架.md --state state/project_state.yaml
python scripts/validate_project_state.py state/project_state.yaml --project-root .
```

重点核对：当前模型口径、Formula Trace、Algorithm Trace 与 `not_needed / stepwise / pseudocode` 呈现选择、命题与证明、条件式预处理、主结果质量门、Analysis Necessity Gate 与条件式独立结果深化分析、代码—工作簿—当前 Python/MATLAB 绘图入口—正文证据链、LaTeX 编译和提交包内容。

执行 `final_review_and_delivery` 时读取当前 competition profile、competition Pack、edition rule verification、最终 PDF、`latex_audit_report.yaml` 与 `compile_report.yaml`，并按 `modules/06_review/final_delivery.md#九final-submission-compliance--evidence-sweep` 完成八类动态 coverage，同时消费共用内容审查。新生成的正式终审报告使用 `templates/review/final_review_matrix.yaml`；旧 `scores + hard_fail + evidence` 报告仍可作为兼容输入。

Matrix 中 `unverifiable` 不得改写成 `passed`；未解决 `blocking` 必须有允许的 Hard Fail code；`review_required` 和 warning 均保留证据与处置状态。评分继续使用显式六维分数，不按 finding 数量自动扣分。

对 `stepwise/pseudocode` 小问，核对 current Algorithm ID、核心输入/状态、操作、停止条件和输出，并人工确认论文算法与真实代码实现、约束/命题锚点及工作簿结果一致；`not_needed` 小问不因缺少算法框扣分，也不应残留装饰性 Algorithm 1。机器只核确定性字段和锚点存在性，不从伪代码文字推断算法正确性或收敛性。

新项目每问数值目录只按 `core/output_contract.yaml` 的 **conditional per-question layout contract** 审计：基础三文件始终为当前路径；仅 Analysis Necessity Gate=`required` 时追加 03B代码 与 workbook。历史文档所称“**五文件合同**”在 current 语义中只对应 Gate=`required` 的 total=5 路径，不是无条件默认。

```text
问题X求解/
├─ <项目后端对应主入口：问题X求解.py 或 qX_solver.m>
├─ 问题X求解结果.xlsx
├─ <绘图后端对应 qX_plot.py 或 qX_plot.m>
├─ [同一项目后端对应深化入口：问题X结果深化分析.py 或 qX_analysis.m]    # only Gate=required
└─ [问题X结果深化分析.xlsx]  # only Gate=required and analysis executed
```

Gate=`not_required` 必须有非空 `result_analysis_requirement_reason`，此时缺少 03B 文件不构成 layout finding，也不得写成“稳健性/稳定性已通过”。Gate=`required` 时则必须核对当前 03B 代码、工作簿与状态/哈希链，缺失不得静默豁免。主工作簿 accepted 后冻结主求解脚本，已激活的深化分析使用同一项目后端对应的独立入口；旧单脚本四文件目录、旧 `结果数据表/问题X/` 和旧敏感性与鲁棒性工作簿只能作为历史项目只读兼容输入。

若 `preprocessing_decision=project_level`，同时检查 `数据预处理/数据预处理.py`、已验收 `数据预处理结果.xlsx` 和 Figure Evidence 阶段按 `plotting.backend` 选定的 `data_process.py` 或 `data_process.m`；若为 `not_needed/question_local`，不得因不存在全局预处理目录而扣分。

评分权重以 `config/review_weights.json` 为唯一机器配置。出现硬否决时不得用加权总分掩盖，先按 `reject_or_major_rework` 处理。

`review_report` 和 `final_review_matrix.yaml` 都是内部终审产物，不自动进入 official package。正式提交内容只服从当前已核验 `edition_rules.submission_files` 与现有 submission package validator。

# 竞赛自动选择

从用户明确名称、题面抬头、模板或附件识别 CUMCM、MCM/ICM、电工杯、认证杯。无法识别时使用通用规则，不凭空套用某竞赛格式。竞赛适配器只负责格式与评审侧重点，不覆盖核心建模规则。

机器入口为 `config/competition_profiles.yaml`：

1. `stable` 只保存相对稳定的模板、编译 Profile、语言和 Pack 路径；
2. `edition_rules` 保存页数、匿名、提交文件、AI 披露等时效性规则；
3. `verification_status` 不是 `verified` 时，不得把默认值表述为当届官方要求；
4. 当届规则必须记录 `verified_at` 和官方来源；旧年度规则到期后标记 `expired`，不得静默复用。

竞赛识别与题型分类相互独立：竞赛决定格式和交付约束，题型决定变量、模型、验证和结果表结构。
