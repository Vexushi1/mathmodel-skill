# HSK DOCX 草稿 + LaTeX 终稿数学建模冲奖工作流 Profile

## DOCX 论文排版与返修补充

当输出 DOCX 论文或修改用户已调整过的 DOCX 时，必须执行 `references/hsk_docx_paper_layout_protocol.md`：使用用户最后上传的文档作为底稿，保证表格为原生三线表，图题与图后解释分离，公式居中编号，摘要分段，主要部分分页，附录代码有说明表。



## v6.1.6 核心流程修正：DOCX 草稿 + LaTeX 终稿 + 机理图前置占位后期精修

本版本将工作流从“前期直接 LaTeX 精修、机理图即时绘制”调整为“前期 DOCX 草稿快速闭合逻辑、机理图合同与占位先行、结果稳定后统一精修少量核心机理图、最终 LaTeX 成稿提交”。

执行顺序：审题 → 模型路线 → 变量公式 → 机理图合同与图位占坑 → 代码求解 → 结果图和鲁棒性 → DOCX 草稿 → 后期 SVG/PPT/GeoGebra 精修核心机理图 → LaTeX 终稿 → 评委式审查。

机理图不要求每问单独保留一张；每问必须有机制解释或引用已有机理图合同。全文核心机理图通常控制在 3--6 张，优先保留 S 级图：题目对象抽象、核心公式来源、关键约束机制和临界状态判断。

新增机理图实战判定法：绘图前先回答图前六问，S 级图必须绑定核心公式或约束；通用流程图、无题目对象的算法流程图、无变量装饰图和几何关系不精确的 AI 自动图，不得作为核心机理图。


本 profile 是本 skill 的最高优先级工作流。凡任务涉及数学建模竞赛、赛题分析、建模方案、代码、图表、论文、摘要、DOCX 草稿、LaTeX 终稿、答辩或终稿审查时，优先执行本文件。若本文件与原 skill 的通用表达重复，采用更清晰、更易执行、更少歧义的一种表达；若存在冲突，以本文件为准。

## 1. 总体定位

目标不是快速堆出论文，而是形成可提交、可复现、可解释、可审查、可答辩、图表美观、人工思考证据充分且代码精壮的高质量数学建模作品。默认竞赛包括 CUMCM 国赛、MCM/ICM、美赛、认证杯、电工杯、华中杯、数维杯等；其中 **CUMCM 国赛 LaTeX 模板必须保留并作为中文论文格式基准**。

## 2. 论文成稿默认规则

1. 最终论文默认使用 LaTeX 编写。
2. 国赛中文论文默认基于 `templates/latex/cumcm/cumcmthesis/`，不得删除或替换该模板。
3. 可新增 `templates/latex/cumcm/hsk/hsk_main.tex` 作为更适合 HSK 工作流的主文件，但仍应调用或兼容原 `cumcmthesis.cls`。
4. 图表文件名使用英文；论文内图题、表题、坐标轴、图例默认中文。
5. 正文不堆代码，复杂算法放伪代码、流程图或关键公式；完整代码放附录或独立附件。
6. 论文中不强制放“题目要求覆盖表”；但写作和审稿过程必须内部检查题目要求是否被遗漏。

## 2A. AI 模板感清除规则

终稿阶段必须清除 AI 模板感：删除空泛套话、无证据支撑的优越性表达、冗余模板表、装饰图和不能反向定位到结果证据的结论句；将“模型效果较好”“显著提高”“明显优于”等表述改为具体误差、排名、提升率、稳定性指标、约束违反量或鲁棒性结果。问题分析必须围绕本题对象、核心难点、建模抓手和结果用途展开，禁止只写通用模型名称。

## 3. 默认推进顺序

除用户明确要求跳转外，任何新赛题应按以下顺序推进：

1. 题目理解报告；
2. 考察方向与命题意图；
3. 各小问目标、数据、依赖、题型拆解；
4. 建模路线比较；
5. 最终推荐模型；
6. 数据处理方案；
7. 变量、假设与符号系统；
8. 核心公式框架；
9. 机理图合同、图位占坑和图表分级；
10. 求解流程与代码结构；
11. 代码求解、结果数据、约束检查；
12. 结果图、敏感性、鲁棒性和多算法验证；
13. DOCX 草稿论文；
14. 后期筛选并精修 SVG/PPT/GeoGebra 核心机理图；
15. LaTeX 终稿论文；
16. 终稿审查。

原则：**先审题，后建模；先机制，后公式；先合同占位，后机理图精修；先代码结果闭环，后论文排版；先 DOCX 草稿迭代，后 LaTeX 终稿提交。**

## 4. 题目要求覆盖机制

内部必须建立“题目要求覆盖检查”，用于防止遗漏题干要求。该检查不等同于论文正文表格，除用户要求外不写入论文正文。

内部检查项：

- 题目原文中的每个明确要求是否被识别；
- 每个隐含约束是否被说明；
- 每个小问是否有对应模型、结果、图表或文字结论；
- 是否存在题目要求只在模型中出现、但结论中没有回应的情况；
- 是否存在图表与结论不支撑的情况。

## 5. 模型路线规则

每个小问至少给两条路线：

- 路线 A：经典稳健模型 + 本题改进；
- 路线 B：高级创新模型 / 跨领域融合模型。

每条路线必须说明：核心思想、数学表达、变量闭环、数据支撑、适配性、创新点、局限性、误差来源、求解难度和推荐等级。

高级模型不能只作为名词出现。凡使用 W-DRO、CVaR、MPEC、Stackelberg、ALNS、图神经网络、空间杜宾模型、双重机器学习、贝叶斯层级模型等方法，必须说明：

1. 为什么必要；
2. 需要哪些变量；
3. 数据是否支撑；
4. 计算是否可行；
5. 结果如何解释；
6. 如何检验。

不满足以上条件，应降级为附录拓展或否决。

## 6. 变量与假设规则

建模时必须区分：

- 决策变量；
- 状态变量；
- 中间变量；
- 参数；
- 目标变量；
- 约束变量；
- 评价指标。

每个模型给出 3--5 个核心假设。每个假设必须说明：假设内容、设立原因、与题目条件的关系、对结果的影响、失效偏差和检验方式。

## 7. 数据处理规则

必须显式审计：数据表含义、字段含义、单位、时间粒度、空间粒度、样本范围、关联键、缺失、异常、重复、单位不一致、时间错位。

数据转换需按需说明：标准化、归一化、对数变换、Box-Cox、时间窗口、滞后变量、空间权重矩阵、图结构、类别编码、样本重采样。

没有真实数据时可模拟，但必须说明模拟机制、分布假设、参数来源和适用边界。

## 8. 代码规则

默认 Python，必要时 MATLAB。正式代码必须可运行，包含：

- 路径配置；
- 数据读取；
- 字段检查；
- 空值检查；
- 维度检查；
- 异常处理；
- 特征构造；
- 模型建立；
- 求解；
- 约束违反检查；
- 结果整理；
- 模型检验；
- 可视化；
- 结果保存；
- 主函数入口。

长时间运行模型应有进度条、日志和阶段状态。精简附录代码时，可以删除冗余注释、无意义 print 和重复代码，但不得删除影响复现、图表输出、结果保存和约束检查的核心逻辑。

## 8.1 v6.1.6 Ponytail 代码精简规则

正式代码应执行 `references/hsk_ponytail_code_protocol.md`：不写投机功能，复用已有实现，标准库和成熟科学库优先，不新增无必要依赖，不写单实现抽象、伪灵活配置和未来脚手架。该规则不得压缩数据审计、约束检查、中文结果输出、运行元数据、图表输出和非平凡逻辑最小检查。

代码终审应列出可删除复杂度，并给出 `net: -N lines possible`。
## 8.5 人工思考证据层与机理/推导图规则

对于每个核心小问，除常规结果图、统计图和算法流程图外，必须优先规划本题专属的机理图、几何推导图、临界状态图或结构示意图。该规则用于展示队伍对题目对象和建模机制的真实理解，不得用通用流程图替代。

最低要求：

1. 每个小问至少说明“该问需要什么推理图、图回答什么建模疑问、对应哪一组公式或约束”。
2. 几何、物理、运动、遮挡、碰撞、路径、调度、资源分配、博弈和工程策略类问题，原则上至少包含“机理图 + 临界状态图 + 结果验证图”中的两类。
3. 图中符号必须与变量表、正文公式和代码变量一致。
4. 正文必须通过“由图可见……因此……”引出模型、公式或约束，不能只写模型名和算法名。
5. AI 可以辅助图的规范化绘制，但题意拆解、关键机制、模型取舍和临界判断必须由人主导。

执行文件：`references/hsk_stage_09_mechanism_figure_protocol.md`。


## 9. 图表规则

默认参考 Nature/Science/SCI 论文风格：白底、细线条、色盲友好、字体统一、中文标签、标注不重叠。核心结果优先设计成单图；多问赛题每问至少规划 1--2 张正文核心图。对机理题、几何题、路径题和工程策略题，正文核心图必须包含推理图或临界状态图，其余图表放附录或答辩材料。

图表默认保存：PNG + PDF/SVG。必要时 TIFF。文件名英文。

## 10. LaTeX 写作规则

默认论文结构：摘要、关键词、问题重述、问题分析、模型假设与符号说明、数据预处理、各问题建模与求解、模型检验、敏感性与鲁棒性分析、模型评价与改进、结论、参考文献、附录。

摘要按问题逐项概述方法与结果。正文公式统一编号，图表交叉引用使用 `\cref` 或 `\ref`，三线表优先使用 `booktabs`。

## 11. 终稿审查规则

终稿必须从评委视角检查：审题遗漏、模型堆砌、变量混乱、公式不严谨、数据不支撑、代码不可复现、图表低级、敏感性缺失、鲁棒性缺失、结论空泛、LaTeX 编译错误、图表引用错误、附录缺失。

发现问题时直接指出并给出可执行修正，不做无意义肯定。


## 12. 交付闭环补充规则

本补充规则只增强交付闭环，不改变 DOCX 草稿 + LaTeX 终稿、可复现结果链路和 HSK v6.1.6 阶段流。

1. 结果总清单：`result_manifest.yaml` 默认不强制生成；仅在完整复现包、多算法大量结果、跨聊天交接、终稿审查或用户明确要求时生成，模板见 `templates/shared/hsk_result_manifest.yaml`。
2. 运行元数据：`run_info.json` 默认不强制生成；仅在完整复现包、多算法大量结果、跨聊天交接、终稿审查或用户明确要求时生成，记录运行时间、环境、随机种子、输入输出文件、关键参数、求解器和状态。
3. 约束违反检查：优化、仿真、调度、路径规划和机理约束模型必须输出标准约束违反检查，模板见 `templates/shared/hsk_constraint_violation_check_table.md`。
4. 精壮代码红线：控制单脚本、单函数、函数参数、调试代码、未使用 import 和重复逻辑。
5. 异常处理分级：数据和运行问题分为 Error / Warning / Info，推荐输出数据审计日志或报告。
6. 摘要反推：摘要需覆盖每问方法、核心数值和结论，模板见 `templates/shared/hsk_abstract_result_checklist.md`。
7. 公式—代码闭环：核心公式需回溯到代码变量或函数，模板见 `templates/shared/hsk_formula_code_closure_table.md`。
8. 图表入文检查：核心图表需有数据来源、代码来源、正文解释和结论支撑，模板见 `templates/shared/hsk_figure_paper_check_table.md`。
9. 题型—模型路线索引：路线比较可参考 `references/hsk_model_route_index.md`。
10. 高级模型准入：高级模型需通过 `references/hsk_advanced_model_gatekeeping.md` 的必要性、变量闭环、数据支撑和计算可行性检查。
11. 测试增强：保留 LaTeX 模板编译 smoke test 和 code starter smoke test。

## 模板按需裁剪

检查表、合同表和 QA 表用于内部审查、DOCX 草稿搭建和返修定位，不等于终稿正文必须全部展示。终稿正文只保留能支撑建模、结果、结论和评委理解的内容，冗长检查表默认不入文或放附录。
