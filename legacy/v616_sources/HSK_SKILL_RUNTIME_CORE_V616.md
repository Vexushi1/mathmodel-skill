# HSK Skill Runtime Core v6.1.6

用于放入 ChatGPT 项目“来源”的核心运行文件。它不是完整 skill 的替代品，而是为了让模型无需每次解压 zip，也能快速读取最关键的工作流规则。

## 1. 当前版本

- Skill 名称：`mathmodel-skill-6.1.6-hsk-docxdraft-latexfinal-mechanism-nature-ponytail`
- 主干来源：`HSK DOCX 草稿 + LaTeX 终稿数学建模冲奖工作流`
- 选择性增强来源：机理图前置占位、Nature/SCI 图表增强、Ponytail 代码精简增强
- 核心定位：前期以 DOCX 草稿快速闭合建模逻辑，机理图只做合同与占位；后期在结果稳定后统一筛选并精修少量核心机理图；最终以 LaTeX 规范成稿提交。
- 执行边界：DOCX 只用于前期阅读、修改、协作和框架审查；最终论文仍默认使用 LaTeX，中文国赛默认保留 `cumcmthesis` 模板。用户明确要求直接 LaTeX 初稿、PDF 初稿或终稿修订时，可直接进入对应阶段。机理图增强只强化人工思考证据与建模解释，Nature/SCI 图表增强只强化结果图表证据与审美，Ponytail 只强化代码精简与审查。

## 2. 最高优先级规则

数学建模相关任务默认执行 HSK 工作流。凡任务涉及赛题分析、建模、代码、图表、论文、摘要、DOCX 草稿、LaTeX 终稿、答辩、评分或终稿审查，优先执行本文件。

核心目标：形成可提交、可复现、可解释、可审查、可答辩、图表美观、人工思考证据充分、代码精壮且证据链完整的竞赛论文和附件。

模板按需裁剪：所有检查表、合同表和 QA 表默认服务于内部审查、DOCX 草稿搭建和返修定位，不等于终稿正文必须全部展示。正文只保留能支撑建模、结果、结论和评委理解的内容；完整检查表可放入附录、交接材料或直接不入文。

## 4. 每个小问最低交付

每个小问至少交付：直接目标、隐含目标、题型判断、所需数据与依赖关系、两条模型路线比较、最终推荐模型、变量表、3--5 个核心假设、核心公式/目标函数/约束/指标、求解流程、结果数据、机制解释或已引用的机理图合同、结果图表、结果解释、误差/敏感性/鲁棒性分析和该问结论。

## 5. 机理图前置占位与后期精修规则

1. 每个核心小问必须有机制解释、变量来源说明或约束来源说明，但不强制每问单独保留一张机理图。
2. 审题和建模阶段先建立机理图合同，明确图名、对应问题、图的作用、图中对象、支撑公式、变量链接、评委质疑点、图等级和后期处理方式。
3. 论文草稿阶段先图位占坑，并在正文中预埋“由图可见……因此……”的机制解释。
4. 模型求解、结果图、约束检查和鲁棒性完成后，再统一回头筛选、合并、生成和精修核心机理图。
5. 机理图分 S / A / B 三级。S 级必须后期人工精修；A 级简洁处理；B 级原则上不画。
6. 全文核心机理图通常控制在 3--6 张。几何、物理、路径、碰撞、调度等复杂题可适当增加，但不得为形式感堆图。
7. 机理图默认不强行用 Python 绘制。几何构造图优先 GeoGebra/几何画板/SVG，纯黑白线稿优先 SVG→EMF→PPT 调整，结构示意图优先 PPT/draw.io/SVG，结果图仍优先 Python/MATLAB 可复现绘制。
8. 执行机理图实战判定法：机理图不是流程图，不以展示模型名称为目标，而以解释题目对象关系、核心公式来源、约束成立机制和临界状态为目标。
9. 机理图优先分为五类：对象关系图、公式来源图、约束来源图、临界状态图、策略机制图。公式来源图、约束来源图和临界状态图优先级最高。
10. 每张机理图绘制前必须回答图前六问：解释哪个题目对象、支撑哪个公式/目标函数/约束、必须出现哪些变量、哪些变量不能放、评委应相信什么、没有该图正文哪段说不清。
11. S 级机理图必须至少绑定 1 个核心公式或 1 组核心约束；凡不能绑定核心公式、约束或结论的图，应降级为文字说明或删除。
12. 图中只画对象关系、变量、方向、边界、距离、角度、流向、决策顺序和临界状态；完整公式推导写在正文，不塞入图内。
13. 通用输入—模型—输出流程图、无题目对象的算法流程图、没有变量符号的装饰图、几何关系不精确的 AI 自动图，不得作为核心机理图。


## 6. 模型路线比较硬规则

每问至少两种路线：经典稳健路线 + 本题改进或高级创新路线。模型路线比较必须包含：核心思想、数学表达、本题适配性、创新点、精度优势、局限性、误差来源、求解难度、推荐等级。

高级模型必须通过准入检查：经典模型为何不足、变量是否闭合、数据是否支撑、竞赛时间内是否可求解、结果是否可解释、是否能检验或验证、是否能通过机制解释或结构图说明。不能回答则降级为备选验证或否决。

## 7. 数据与代码核心规则

必须审计字段含义、单位、时间粒度、空间粒度、样本范围、关联键、缺失值、异常值、重复值、单位不一致、时间错位。

默认 Python，必要时 MATLAB。代码必须可运行、模块化、可复现，不写大而全工具箱。必须包含路径配置、数据读取、字段检查、空值检查、维度检查、异常处理、随机种子、特征构造、模型求解、约束违反检查、结果保存、图表保存、主函数入口。

精壮红线：单脚本原则上 300--500 行以内；单函数原则上 80 行以内；单函数参数原则上 8 个以内；未使用 import、调试 print、重复逻辑不进入最终版。

## 8. Ponytail 代码精简规则

代码阶段执行 `references/hsk_ponytail_code_protocol.md`。默认强度为 full，但不使用 ultra 作为数学建模默认。

代码精简阶梯：不写无论文用途的投机功能；复用项目内已有函数；优先标准库；优先成熟科学计算库；不为几行逻辑新增依赖；能用短函数解决就不写类、工厂、接口或框架；最后才写最小可用代码。

不得为了精简删除：路径配置、随机种子、数据审计、目标函数、约束函数、约束违反检查、`data_output/` 输出、图表输出、图表绘制代码和非平凡逻辑的最小检查。若本次任务已启用 `run_info.json` 或 `result_manifest.yaml`，则不得在瘦身阶段删除。

代码瘦身审查格式：

```text
文件:L行号: tag: 问题。替代方案。
net: -N lines possible.
```

标签包括 `delete`、`stdlib`、`native`、`yagni`、`shrink`。若没有可删项，输出 `Lean already. Ship.`。

## 9. 图表规则

机理/推导图用于说明题目对象、公式来源、约束机制和临界状态；结果图用于展示求解结果、对比、敏感性、鲁棒性和策略效果。

所有核心结果图必须建立 Nature / SCI figure contract：Core conclusion、Figure role、Panel map、Source data、Plot code、Export files、Reviewer risk。机理图必须建立 mechanism contract：图中对象、支撑公式/约束、变量链接、评委质疑点、图等级和后期处理方式。

图表主链路：题意对象/机制解释 → 数学公式 → 代码计算 → `data_output/` 中文结果数据 → `figures/` 论文图 → DOCX 草稿引用 → LaTeX 正文引用 → 图注解释 → 结论支撑。

## 10. DOCX 草稿与 LaTeX 终稿

DOCX 草稿用于模型、结果和正文逻辑尚未锁定时的快速浏览、人工修改和协作批注。它不替代最终 LaTeX 论文，也不承担最终排版任务。

最终论文默认使用 LaTeX。中文国赛论文默认基于 `cumcmthesis` 模板，保留国赛模板体系。进入 LaTeX 终稿前，应完成模型与结果锁定、核心机理图精修、结果图从代码重新导出、表格转三线表、公式编号和交叉引用统一、参考文献和附录补齐。

## 11. 结果输出与提交闭环

默认按小问分目录输出，避免所有结果堆在同一层级：

```text
data_output/
  problem1/
    数据结果/
    图表/
  problem2/
    数据结果/
    图表/
```

输出数据表文件名使用中文，表格内部字段名和行列名使用英文；图像文件名建议使用英文或拼音，论文内图题、表题、坐标轴和图例默认中文。

`run_info.json` 和 `result_manifest.yaml` 默认不强制生成；仅在完整复现包、多算法大量结果、跨聊天交接、终稿审查或用户明确要求时生成。优化、仿真、路径、调度和机理约束模型仍应输出必要的 `问题X约束违反检查.csv`；普通描述统计、评价、聚类类任务可说明不适用。可编辑机理图建议进入 `figures_editable/`；DOCX 草稿建议进入 `draft_docx/`；LaTeX 终稿建议进入 `final_latex/`。

终稿必须检查：题目要求是否回应、模型是否契合题意、人工思考证据是否充分、AI 模板感是否清除、变量公式是否闭合、代码是否可复现、约束是否满足、图表是否支撑结论、DOCX 占位是否全部处理、LaTeX 编译和引用是否闭合。


## 12. AI 模板感清除终稿硬规则


终稿阶段必须执行 AI 模板感清除，目标是删除空泛、模板化、无证据支撑的表达，使论文呈现为由题意、机制、数据和结果共同驱动的人工建模文本。

1. 删除“具有重要意义”“提供参考价值”“较好地解决”“具有一定优越性”等不能直接对应结果证据的空泛评价。
2. 删除重复机械的“首先、其次、最后”等套话式段落连接；需要保留层次时，改为围绕题目对象、变量关系、约束机制和结果证据组织。
3. 删除没有数据、误差、排名、提升率、稳定性指标、约束违反量或鲁棒性结果支撑的“显著提高”“明显优于”“效果较好”“稳定性较强”。
4. 删除正文中过多的路线比较表、检查表、合同表和 QA 表；终稿正文只保留支撑建模理由、公式来源、结果解释和结论证明的必要内容。
5. 删除不能支撑结论的装饰图、通用输入—模型—输出流程图和无题目对象的算法流程图；图表必须绑定具体小问、公式、约束、数据或结论。
6. 将“模型效果较好”类表述改写为可复核表达，例如具体误差、排名变化、提升比例、置信区间、扰动幅度下的结果变化、约束最大违反量或多算法一致性结果。
7. 将模板化问题分析改写为本题对象、核心难点、建模抓手和结果用途；禁止只写“本问建立评价/优化/预测模型”。
8. 删除没有在正文中被公式、图表、数据或代码结果支撑的结论句；若结论重要但缺证据，应补检验或降级为讨论。

最低改写标准：每个核心结论都应能反向定位到正文公式、结果表、结果图、约束检查、敏感性/鲁棒性分析或附录代码输出；无法定位的结论不得作为终稿结论保留。

## 12A. DOCX 论文草稿排版与图文证据链硬规则

当用户要求输出 DOCX 论文稿、Word 初稿，或基于用户已经修改过的 DOCX 继续加工时，必须同步执行 `references/hsk_docx_paper_layout_protocol.md`。核心规则如下：

1. **底稿优先**：用户上传已修改 DOCX 后，以该文件为唯一底稿继续修改，不得回退旧稿或重建覆盖用户格式。
2. **正文格式**：中文宋体、英文 Times New Roman、小四、两端对齐、段前段后 0、首行缩进 2 字符、1.5 倍行距。
3. **标题格式**：一级标题居中且黑色，禁止 Word 默认蓝色标题样式污染论文。
4. **表格真表格**：正文和附录表格必须为 Word 原生表格，禁止图片表格；三线表只保留表顶线、表头下线和表底线。
5. **图题和解释分离**：图题只写“图号 + 图名”，图下另起正文段写“由图X可知……”，解释图表结论和对后文的支撑，不把解释塞进图题。
6. **图后解释保留**：不得删除核心图后的解释段；应把零散短句整合成一个自然段。
7. **公式居中编号**：核心公式单独成行、居中、连续编号，公式前说明来源，公式后解释含义。
8. **摘要分段**：摘要不得写成一个大段，应按研究背景、模型一、模型二、模型三、稳健性和政策含义分段，并写入核心数值。
9. **分页**：摘要、目录、正文、参考文献、附录等主要部分应分页处理；若设置致谢，致谢应单独分页。
10. **伪代码与代码附录**：正文放精简伪代码，完整代码放附录或附件；每份代码前必须有代码说明表。

输出 DOCX 前必须用 `templates/shared/hsk_docx_layout_checklist.md` 做格式硬检查。
