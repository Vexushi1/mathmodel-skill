## 2. Architectural invariant: primary quality vs result analysis

This is the most important v7.14 invariant.

### 2.1 Primary quality question

Primary quality checks answer only:

> **Under the current locked model and the declared numerical method, is this specific primary computation numerically admissible enough to become an accepted solution workbook?**

If a check fails and the current result itself cannot be accepted, it belongs to primary quality.

Typical primary-quality evidence:

- execution provenance and full-fidelity configuration;
- solver stop status that is required to interpret the returned solution;
- explicit-constraint violation;
- equality / equilibrium / conservation residual when required by the current model;
- boundary-condition residual where the current numerical model requires it;
- discretization adequacy when the answer depends on grid / step / resolution;
- convergence adequacy when the answer depends on iterative convergence or simulation length;
- exact/relaxation bound or reported optimality gap when this is part of the solver's own validity claim;
- minimum sampling precision needed for the primary Monte Carlo/statistical estimate itself;
- one legitimate out-of-sample evaluation when prediction validity itself requires it;
- leakage/calibration/identifiability checks only when the relevant capability is active and failure would invalidate the primary result.

### 2.2 Result-analysis question

Result analysis starts only after `accepted_solution_workbook` and asks:

> **Given an accepted primary result, how stable is the conclusion under perturbations, alternative structures/methods, broader scenarios, heterogeneous groups, or claim-boundary analysis?**

These remain exclusively in Module 03B unless they are definitionally part of one execution of the primary algorithm:

- parameter sensitivity;
- threshold / failure-boundary exploration beyond minimum numerical admissibility;
- scenario stress testing;
- alternative algorithm comparison;
- repeated multi-start / multi-seed robustness when used to assess conclusion stability;
- structural robustness / alternative model comparison;
- heterogeneity analysis;
- error decomposition;
- broader multi-window / multi-domain out-of-sample stability;
- ablation or model-component importance analysis.

### 2.3 Mandatory boundary sentence for the new Authority

The new Authority must contain a normative statement equivalent to:

> Primary quality checks shall only test whether the current primary computation is numerically admissible under the locked model and declared numerical method. They shall not evaluate sensitivity to model parameters, alternative structures, alternative algorithms, stress scenarios, heterogeneous groups, or broader claim stability; those belong exclusively to result analysis after the primary workbook is accepted.

### 2.4 Ambiguous cases

- **Discretization vs sensitivity**: numerical step/grid/resolution adequacy → primary; physical/model parameter perturbation → analysis.
- **Monte Carlo sample count vs multi-seed robustness**: minimum MC error/sample-length adequacy for the reported primary estimate → primary; repeated seeds to establish conclusion stability → analysis.
- **Solver gap vs algorithm comparison**: current solver's bound/gap/termination evidence → primary; MILP vs ALNS vs GA vs greedy → analysis.
- **OOS test vs OOS stability**: one valid held-out/rolling test required to validate the primary prediction → primary; many windows/regions/regimes/transfer settings → analysis.

## 3. New single authority: `core/numerical_verification_contract.yaml`

Add one new contract and make it the only field-level authority for primary numerical validity.

It should define:

1. `contract_version` and `skill_compatibility` metadata;
2. scope and explicit non-scope;
3. mapping from active capabilities to **primary-quality evidence protocols**;
4. minimum evidence fields per protocol;
5. deterministic consistency rules the validator may recompute;
6. threshold provenance rules;
7. blocking / not-applicable semantics;
8. compatibility behavior for old workbooks without v7.14 verification IDs;
9. boundary pointer to Module 03B for all post-acceptance robustness/deep analysis.

Do **not** duplicate complete sheet schemas here. Sheet columns remain owned by `core/workbook_schema.yaml`; the numerical contract should reference them.

Initial protocol families should stay small and competition-relevant:

- `feasibility`
- `equilibrium_residual`
- `conservation_residual`
- `discretization_adequacy`
- `convergence_adequacy`
- `out_of_sample_primary_validity`
- `uncertainty_precision`
- `leakage_primary_validity`
- `calibration_primary_validity`
- `identifiability_primary_validity`

Do not introduce `parameter_sensitivity`, `scenario_stress`, `algorithm_robustness`, `structural_robustness`, or `heterogeneity` as primary-quality protocols.

## 5. Primary quality specification

Do not create a free-floating project file by default. Extend the existing model-design validation semantics so the current framework/state can carry a structured **Primary Quality Specification** (PQS) as part of the current validation plan/model framework.

A PQS item should minimally express:

```yaml
id: PQ-Q1-01
capability: requires_feasibility_check
protocol: feasibility
target: current solution feasibility
metric: max_constraint_violation
criterion:
  operator: "<="
  threshold: 1.0e-6
  source: locked_model_or_solver_tolerance
evidence_sheet: 约束违反检查
blocking: true
```

Rules:

- PQS is fixed before formal primary code is generated.
- Thresholds must have provenance: problem requirement, mathematical definition, solver tolerance, numerical-method accuracy target, or explicitly justified project criterion.
- Arbitrary thresholds introduced only after seeing favorable results are forbidden.
- PQS may define a family of evidence rows rather than hardcoding every runtime value.
- `result_analysis_plan` is **not** generated from PQS; it remains a separate post-acceptance artifact based on actual primary results and risks.

## 6. Workbook semantics

Preserve `core/workbook_schema.yaml` as the only sheet/column authority.

Use existing capability sheets wherever possible. Strengthen the main-quality linkage instead of proliferating worksheets.

The `主结果质量门` should evolve from a self-declared Boolean summary toward a traceable summary such as:

- `Verification ID` (new, for v7.14 writers)
- `检查项`
- `指标` (optional where needed)
- `是否通过`
- `证据`
- `阈值或容差`
- `实际值`
- `证据工作表` (new, recommended/required for machine-verifiable checks)
- `阈值来源` (new, to prevent post-hoc thresholds)
- `说明`

Exact required/optional status must be selected conservatively to preserve v7.13 read compatibility.

Capability-specific evidence tables should continue to contain bottom-level data, not only summary declarations. For example:

- constraint rows: violation + tolerance + whether satisfied;
- conservation/equilibrium: residual + tolerance + whether satisfied;
- discretization: resolution/step + target quantity + relative change;
- convergence: iteration/sample count + metric/value + judgement;
- uncertainty: lower/upper + confidence/quantile/sample count where available;
- calibration: predicted probability + observed frequency, with Brier/ECE optional;
- identifiability: method + conclusion, with rank/condition number/CI where available.

## 7. Independent numerical evidence validator

Add `scripts/validate_numerical_evidence.py` as a narrow reusable checker.

Responsibilities:

- read the current capabilities/PQS and workbook;
- confirm required evidence sheets/columns for active primary-quality protocols;
- recompute deterministic Boolean consistency where possible;
- reject contradictory rows such as `违反量 > 容差` but `是否满足 = 是`;
- verify that quality-gate summary links to real evidence;
- verify threshold/provenance presence for machine-verifiable v7.14 checks;
- return structured issues/pass status to callers.

Non-responsibilities:

- no task-specific model solving;
- no parameter sensitivity;
- no scenario stress;
- no alternative algorithm/model robustness;
- no claim support/modify/reject disposition;
- no rewriting user workbooks.

`validate_user_execution.py` should call this checker after provenance/configuration checks and before marking the primary workbook accepted.

## 8. Protocol-specific v7.14 behavior

### 8.1 Feasibility

For inequality violation value `v` and declared tolerance `eps`, independently require `v <= eps` for rows declared satisfied. Equality residuals use absolute residual unless the contract specifies a normalized residual field.

### 8.2 Equilibrium / conservation

Validate row-level residual vs tolerance consistency. Where normalized residual is used, the numerical method/model must define the normalization; the validator must not invent physics-specific normalization from generic columns.

### 8.3 Discretization adequacy

Primary purpose: establish that the chosen primary grid/step/resolution is adequate for the reported answer.

Minimum generic rule should be based on the final refinement levels and declared project tolerance. Optional empirical order is allowed only when mathematically meaningful; it must never be forced on event-driven/discrete-search problems.

### 8.4 Convergence adequacy

Separate solver stop reason from convergence evidence. `time_limit` / `max_iter` must not be auto-translated to convergence. The protocol may accept a non-optimal but explicitly bounded status only if the model/PQS permits that claim level.

### 8.5 Uncertainty precision

Primary quality covers only the minimum sampling/interval precision needed to make the reported primary estimate admissible. Multi-seed robustness and scenario robustness remain analysis.

### 8.6 OOS / leakage / calibration / identifiability

Only enforce when the capability is active. Primary OOS means one legitimate validation design required to substantiate the main predictive/inferential result; broader stability belongs to Module 03B.

## 9. Main-solve code generation constraints

Update Module 03A and starter guidance so `问题X求解.py` remains compact:

```text
input/data-source checks
→ locked primary model
→ primary solve
→ only mandatory intrinsic numerical-validity checks from PQS
→ main answer/workbook
→ primary quality summary
```

Explicitly forbid automatic insertion of:

- broad parameter sweeps;
- stress-scenario suites;
- alternative model/algorithm comparison;
- repeated-seed stability reports;
- heterogeneity analyses;
- paper-facing robustness matrices.

If one primary algorithm internally requires multiple starts/seeds as part of its defined solve procedure, they may remain inside one primary execution, but post-hoc stability claims still belong to Module 03B.

## 10. Result analysis protection

Module 03B should gain a short explicit protection clause:

- starts only after primary acceptance;
- remains owner of post-acceptance sensitivity/robustness/boundary/comparison work;
- v7.14 primary validation must not precompute or duplicate its evidence;
- analysis may still send the workflow back to solve/model design if accepted-result assumptions later fail under evidence disposition rules.

Do not weaken the existing `support / modify / reject` semantics.

## 12. Version and compatibility policy

Target `7.14.0` because this is a backward-compatible new capability and validation layer.

Compatibility requirements:

- old v7.13 workbooks remain readable;
- v7.14 writers emit verification trace fields;
- strict machine recomputation is required for newly declared v7.14 primary verification evidence;
- old workbooks without `Verification ID` may use legacy acceptance semantics when being read as historical accepted artifacts;
- an old project that re-enters current primary solving should migrate that question to v7.14 evidence semantics;
- no directory rename;
- no removal of old CLI;
- no forced migration of historical projects.

## 13. Testing plan

### Governance minimum

```bash
python scripts/lint_skill.py

python scripts/generate_indexes.py --check
```

### Targeted regressions

New v7.14 tests should cover at least:

1. **Primary/analysis boundary**
   - numerical contract explicitly excludes sensitivity, stress, alternative algorithms/structures, heterogeneity;
   - Module 03A does not claim these outputs;
   - Module 03B retains ownership.

2. **Contradictory feasibility evidence**
   - `violation > tolerance` with `是否满足 = 是` must fail.

3. **Contradictory residual evidence**
   - residual > tolerance with `是否满足 = 是` must fail.

4. **Quality summary traceability**
   - v7.14 verification row pointing to a missing evidence sheet must fail.

5. **Threshold provenance**
   - newly generated v7.14 machine-verifiable gate without threshold source must fail when the protocol requires one.

6. **Discretization admission**
   - final refinement change above declared tolerance cannot be declared passed;
   - convergence-order calculation is not universally mandatory.

7. **Termination semantics**
   - `max_iter` / `time_limit` cannot by itself mean converged/optimal.

8. **Backward compatibility**
   - representative v7.13-style workbook can still be read under compatibility mode;
   - new writer emits v7.14 fields.

9. **Route/dependency closure**
   - solve/returned-workbook routes load numerical contract/checker dependency;
   - figure/latex-only routes do not preload it without need.

10. **Version parity**
    - all current version carriers resolve to current Bootstrap version, not hardcoded release strings in upgrade-sensitive tests.

## 15. Stop conditions during implementation

Stop and reassess before further writes if any of these occur:

- another open PR starts modifying the same authorities;
- `main` moves and the branch becomes meaningfully behind before PR creation/final validation;
- implementation requires changing project directory layout or making v7.13 workbooks unreadable;
- the numerical checker begins needing task-specific model solving;
- a proposed primary protocol requires parameter sensitivity / stress / alternative-method evidence to decide basic admissibility;
- more than one file starts independently defining the same numerical threshold rules;
- the work expands into mechanism taxonomy, solver benchmark corpus, or competition-edition intelligence.

Those are separate future releases.

## 16. Acceptance definition for v7.14

v7.14 is complete only when all of the following are true:

- primary quality vs result analysis is explicitly and consistently separated across contract/module/runtime/test layers;
- at least feasibility/residual/discretization/convergence evidence can be independently cross-checked rather than trusted from a self-declared Boolean alone;
- newly generated primary workbooks can trace main-quality rows to bottom-level evidence;
- old v7.13 projects remain readable;
- no task-specific full-fidelity computation moves to Assistant execution;
- result-analysis script remains independent and post-acceptance;
- generated metadata is current;
- lint, full unit tests, required targeted tests and full GitHub CI pass on the final PR head.

If any acceptance item fails, the PR is not merge-ready.
